## 二、三个真问题

### 问题一：功能「有壳没肉」

14 个页面里，真正闭环的只有清理和查重。其余多数停在「能看」：

- **软件页**只列清单，不能卸载、不能看占用、不能查残留
- **大文件**只能看，不能批量删/移
- **启动项**能看到计划任务，但没有独立的任务管理
- **体检** 11 项里 2 项永远灰着（社交缓存、注册表）

对比 GrClean 的 26 个功能页，缺口在：**社交软件专清、注册表、卸载残留、回收站、右键菜单、系统快照、目录迁移、驱动/更新**。

### 问题二：逻辑断层（最要命）

**现状数据流是「各自为政」：**

```
清理页 ──扫描──> 自己的 _items ──> 汇总数字
查重页 ──扫描──> 自己的 _groups ──> 汇总数字
启动项 ──扫描──> 自己的 _entries
                    │
                    │ 只能靠主窗口手工缓存三个数字
                    ▼
体检页 ──「全面体检」──> 把上面三个扫描**重新跑一遍**
```

三个后果：

1. **重复劳动**。全面体检要重新扫垃圾、重新查重，明明清理页刚扫过。
2. **数字会打架**。清理页显示 75 MB，体检显示 80 MB（扫描时间不同）。
3. **「一键优化」名不副实**。点下去只做内存整理（`optimizer.optimize` 只 trim 工作集），
   跟用户理解的「一键把系统弄干净」完全不是一回事。

**这是用户说「逻辑关系搞清」的真正所指。**

### 问题三：UI 同构，缺节奏

14 个页面几乎都是同一个模子：

```
大标题 + 副标题
[KPI 卡 ×4]
[卡片：图表 / 列表 / 表格]
```

结果：

- **概览页**该是「一眼看全局」，现在信息密度过低，大片留白
- **每个页面**都从零开始，没有跨页面的上下文
- **图表**是自绘的简单折线，无网格、无 hover 数值、无时间轴刻度
- **空状态**全是「尚未扫描」，没有引导动作
- **深色主题**正文 `#C8C8C8` 对比度偏低，长时间看累

## 三、逻辑重构（P0，先做这个）

### 3.1 目标分层

```
┌─────────────────────────────────────────────┐
│  UI 层（页面只订阅，不扫描）                  │
│  概览 / 清理 / 查重 / 体检 …                  │
└───────────────┬─────────────────────────────┘
                │ 订阅 + 派发任务
┌───────────────▼─────────────────────────────┐
│  状态层 core/store.py   ← 单一数据源          │
│  junk / dup / startup / software / health    │
└───────────────▲─────────────────────────────┘
                │ 写回结果
┌───────────────┴─────────────────────────────┐
│  编排层 core/task.py   ← 任务中心             │
│  队列 / 进度 / 取消 / 日志 / 串行保证         │
└───────────────┬─────────────────────────────┘
                │ 调用
┌───────────────▼─────────────────────────────┐
│  能力层                                       │
│  采集 probe/*  · 分析 analyze/*  · 执行 act/* │
└─────────────────────────────────────────────┘
```

三条硬规则：

1. **页面不持有业务数据**，只从 `store` 读、往 `task` 派。
2. **任何扫描结果都写回 store**，谁扫的都一样，全应用共享。
3. **执行类操作（删除/禁用/优化）必须可回滚**，走 `act/*`，统一进回收站或生成 undo 记录。

### 3.2 任务中心

现在的扫描是「页面级 QThread」，切走页面就断了。改成全局任务：

```python
class TaskCenter(QObject):
    task_started = Signal(str, str)      # id, 描述
    task_progress = Signal(str, int, str) # id, 百分比, 文案
    task_finished = Signal(str, object)   # id, 结果
```

好处：

- 查重跑 5 分钟，用户可以切到别的页面，右下角显示「正在查重 42%」
- 多个扫描排队串行（GrClean 的教训：并发扫盘不是更快，是更慢）
- 体检不再自己扫，直接读 store；store 没有数据才派任务

### 3.3 「一键优化」的真实链路

```
1. 检查回收站占用        → 提示可清空
2. 扫描垃圾（复用 store） → 清理
3. 扫描重复文件（10MB+）  → 每组留一份，其余进回收站
4. 检查启动项             → 列出「建议禁用」但不自动禁用
5. 整理内存工作集         → 现有的 optimizer
6. 生成报告               → 释放 X GB / 建议 Y 项 / 一键回滚
```

**默认只执行 1/2/5（低风险），3/4 需要用户确认。** 报告页给出明细和「撤销」入口。

## 五、UI 整改清单

### 5.1 结构层

| 问题 | 改法 |
|---|---|
| 14 页同构 | 定三种页面模板：**看板型**（概览）、**清单型**（清理/查重/大文件）、**表单型**（设置/系统信息）。同类页面复用骨架，异类页面明确差异化 |
| 概览信息密度低 | 上半屏改成「系统状态带」：一行横贯的健康分 + 4 个指标 + 最近一次优化结果；下半屏放「待处理事项」列表（可直接跳转） |
| 无跨页上下文 | 顶部常驻一条状态栏：`上次体检 2 小时前 · 可清理 1.4 GB · 3 项建议` |

### 5.2 视觉层

| 问题 | 改法 |
|---|---|
| 图表太素 | 统一换成带网格 + hover 数值 + 时间轴刻度；折线下方加渐变填充；补 1 小时/6 小时/24 小时切换 |
| 空状态粗糙 | 每个空态给一个明确的按钮（「开始扫描」），配一句说明「扫什么、大概多久」 |
| 深色对比度低 | 正文 `#C8C8C8` → `#D6D6D6`；辅助文字 `#8F8F8F` → `#9A9A9A` |
| 数字不齐 | 所有数值列启用等宽数字（`tabular-nums`），表格不再跳动 |
| 缺动效 | 扫描进度、数值变化加 200ms 过渡，避免数字硬跳 |

### 5.3 交互层

| 问题 | 改法 |
|---|---|
| 长任务无法离开页面 | 任务中心浮层（右下角），可展开看进度/取消 |
| 删除不可撤销 | 统一「最近操作」记录，支持一键撤销（回收站 + 注册表备份） |
| 无快捷键 | `Ctrl+1..9` 切页，`F5` 重新扫描，`Ctrl+,` 设置 |
| 危险操作提示弱 | 二级确认 + 影响范围预览（「将删除 1,234 个文件，共 3.2 GB」） |

## 七、取舍与风险

**不建议做的：**

- **系统精简 / 组件移除**（GrClean 有）—— 风险极高，一次误删可能导致系统更新失败，收益不成正比
- **驱动自动安装** —— 变砖风险，只做「提示可更新」
- **多语言** —— 用户是中文环境，投入产出比低

**必须守住的红线：**

1. 任何删除都进回收站，注册表操作先导出备份
2. 系统目录、程序目录、用户文档目录默认不碰（现有 `safety.py` 已实现，保持不变）
3. 不静默执行高风险操作，一律二次确认

**主要风险：**

| 风险 | 应对 |
|---|---|
| 重构期功能回退 | 每阶段独立可发布，不追求一次到位 |
| 注册表操作翻车 | 只做「扫描 + 导出」，删除做成显式可选，且逐条确认 |
| 社交缓存误删聊天记录 | 严格白名单路径（`FileStorage\Cache` 等），不碰 `Msg` 数据库目录 |
| 任务中心引入并发 bug | 强制串行队列，不做并发 |

## 八、优先级建议

如果只能做一件事：**先做阶段一**。

现在功能不算少，是「散」。数据通了、任务通了，后面加功能是线性的；数据不通，每加一个功能都要再写一遍扫描和缓存，越加越乱。
