## 一、这是什么

一个 Windows 桌面端系统管理工具，PySide6 写的单文件 exe。

核心能力：实时监控（CPU/内存/磁盘/网络/进程）、系统信息、垃圾清理、软件专清、
重复文件、磁盘空间、回收站、开机启动、注册表清理、软件管理与卸载残留、
健康度体检、一键优化、系统瘦身（关更新自动安装、遥测与推荐位，可逐项还原）。

**定位**：轻量、纯本地、不联网。系统级改动只做「改一个已知策略值、随时能改回来」
的那一类，不碰 Defender、防火墙、系统还原、页面文件。

## 二、五分钟上手

```bash
# 开发运行
python main.py

# 打包（约 1 分钟，输出 dist/Windows系统管家.exe）
python tools/build.py

# 重新生成图标（改了 ui/appicon.py 之后）
python tools/make_icon.py
```

依赖只有两个：`PySide6-Essentials`、`psutil`。见 `requirements.txt`。

**打包时如果旧版本正在运行**，`dist/` 里的 exe 删不掉，脚本会自动输出到
`dist_pending/`，并提示你手动覆盖。

## 三、架构

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│ UI 层  ui/page_*.py                          │
│ 只做三件事：订阅 store 信号 → 派任务 → 渲染    │
│ 不持有业务数据，不起线程                       │
└───────────────┬──────────────────────────────┘
                │ 订阅 + submit
┌───────────────▼──────────────────────────────┐
│ 状态层  core/store.py   ← 单一数据源           │
│ junk / dup / bigfile / startup / registry     │
│ / software 七个状态对象                       │
└───────────────▲──────────────────────────────┘
                │ apply(task_id, result)
┌───────────────┴──────────────────────────────┐
│ 编排层  core/task.py   ← 全局任务中心          │
│ 串行队列 / 进度 / 取消 / 失败兜底              │
└───────────────┬──────────────────────────────┘
                │ 调用
┌───────────────▼──────────────────────────────┐
│ 能力层  core/*.py                             │
│ cleaner / dup / bigfile / startup / registry  │
│ / recycle / social / health / sysinfo …       │
└──────────────────────────────────────────────┘
```

### 3.2 一条数据怎么流动

```
用户点「扫描」
  → page.start_scan()
  → tasks.submit("junk", "扫描垃圾文件", fn)
  → TaskCenter 串行执行 fn(report, should_stop)
  → 返回 JunkState
  → MainWindow._on_task_finished → store.apply("junk", state)
  → store.junk_changed 信号
  → 清理页重画 / 概览页重排建议 / 体检页重算分数
```

**这就是整个项目最重要的一条链路。** 数据只写一次，三个地方同时更新，
不需要任何手工同步。加新功能时请沿用这个模式，不要回到「页面自己扫自己存」。

### 3.3 体检为什么要拆两半

`health.probe_system()` 开物理磁盘句柄、读注册表，**79ms**，慢。
`health.collect(snapshot=...)` 只重算分数，**0.1ms**。

体检页缓存 snapshot，垃圾/重复文件一变就重算，不重新探测。
所以「清理页扫完 → 体检页分数立刻变」，用户不用再点「全面体检」。

## 五、功能现状

### 5.1 导航结构（14 项，三组）

| 分组 | 页面 |
|---|---|
| 概览 | 全面体检、性能监控（页内分段：总览 / CPU / 内存 / 磁盘 / 网络 / 进程） |
| 清理 | 垃圾清理、软件专清、重复文件、磁盘空间、回收中心 |
| 管理 | 开机启动（分段：全部 / 注册表 / 启动文件夹 / 计划任务）、系统瘦身、软件管理（分段：已安装程序 / 卸载残留）、注册表项 |
| 底部 | 系统信息、偏好设置、关于软件 |

**计划任务已并入「开机启动」。** 原来两页读的是 `startup.list_entries()` 的同一份
结果、写的是 `store.startup` 的同一个字段：谁扫一次就覆盖对方的列表，而两边
`task_id` 还不一样，各自判定「对方在忙」，点刷新毫无反应。合并后一次扫描拿全三处
来源，顶部用分段筛选，计划任务多出来的「下次运行」单独占一列。

**入口少的页面用分段，不新开导航项。** 磁盘空间（分析 / 大文件）、软件管理
（已安装 / 卸载残留）、性能监控（六个分段）都是这个套路：同一件事的不同侧面，
分到两个入口会让人以为要分两次操作。

**名称一律四个字。** 2/3/4 字混排时右边缘参差，看着像没对齐；压到两字又做不到
（「大文件」「回收站」「注册表」压成「文件」「回收」「注册」会失真），所以统一往
四字扩写，不改概念。`key` 是页面标识，改显示名不影响跳转，页面内文案不用跟着改。

**默认启动页是「全面体检」**（`_current_page` 初值一处即可，`_build_content`
末尾按这个值建首屏）。打开软件想知道的第一个问题是「这台机器现在怎么样」，
体检页直接给分数和待处理项；性能监控是一屏实时数字，看完还得自己判断，排第二位。

**分组标题由 `_nav_group_label` 出**，22px 高、11px 号 `TEXT_DIM`；三组共 66px，
靠行高 36→32 省下来的 40px 补回来，整块高度和改之前基本持平。旧版分组之间只画
1px 细线、不写字，等于把分组信息丢了 —— 十二个入口平铺，找东西全靠逐行读。

**图标语义不能重复。** 垃圾清理 = 垃圾桶，回收中心 = 循环箭头（`recycle`）。
旧版两个入口共用一只垃圾桶，扫一眼分不出「清垃圾」还是「看回收站」。扫帚试过两版
（扇形刷头、三根刷毛），16px 下都读成对勾，已放弃 —— 小尺寸图标先渲染出来看，
别靠脑补。

快捷键：`Ctrl+1..9` 按侧栏顺序对应前 9 项，`Ctrl+0` 给第 10 项（系统瘦身）——
数字键只够 10 个，底部三项不占：系统信息与关于都是纯查看页，偏好设置用 `Ctrl+,`。
`F5` 重扫当前页，`F1` 直接翻到「关于软件」。

### 5.3 软件列表的数据边界

`core/apps.py` 现在是**双来源**：注册表 `Uninstall` 键 + 安装目录扫描。
只读注册表会整类漏掉国产网游客户端（梦幻西游、多数自研启动器装的游戏），
它们压根不写 Uninstall 键——这是用户反馈「我装了但列表里没有」的根因。

| 来源 | 怎么认 | 覆盖 |
|---|---|---|
| 注册表 | `HKLM/HKCU\...\Uninstall` 三个视图（64/32 位 + 当前用户） | MSI / NSIS / Inno 等正规安装包 |
| 安装目录 | 固定磁盘根 2 层、`Program Files(+\x86)` 3 层、`%LOCALAPPDATA%\Programs` 2 层里，目录下存在 `uninstall.exe` / `uninst*.exe` / `卸载*.exe` | 网游客户端、绿色版、自家启动器装的软件 |

| 现象 | 原因 | 现状 |
|---|---|---|
| 列表仍少于「设置→应用」 | Store/MSIX 应用在 `AppxAllUserStore` 里；连卸载器都没有的纯绿色版 | 拿不到（要补需调 `Get-AppxPackage`，几百个内置应用，默认不做） |
| 有名字但没卸载按钮 | 该项没有可用的卸载命令 | 保留在列表里，右键菜单禁用并说明「未提供卸载程序」 |
| 版本/发行商是「—」 | 目录扫描项只能从 exe 版本资源里挖 | 卸载器没有版本资源时，按体积倒序试目录里前 12 个 exe 凑 `CompanyName` / `FileVersion` |
| 安装日期空白 | 很多安装包不写 `InstallDate`（Electron 系都这样） | 回退取注册表键最后写入时间；目录项取卸载程序的创建时间 |
| 大小显示 — | `EstimatedSize` 未登记且没有可扫的安装目录 | 目录扫描项按实际文件统计；注册表项仍用登记值 |
| 大小显示 <1 MB | 登记的是几 KB 假值 | 不再格式化成「0 MB」 |
| 多出 .NET / WebView2 等 | `SystemComponent=1` | 保留（原来一律丢弃），名称 tooltip 标「系统组件」 |
| 同款软件出现两行 | 注册表 DisplayName 带版本号、目录项只有文件夹名 | 去重先比安装路径，再比归一化名字（忽略空格/`(x64)`） |

去重时注册表那份优先（名字、版本更准），但**卸载命令、安装位置、体积、日期会互相补齐**。
`InstallLocation` 缺失时用 `UninstallString` 反推目录（`"D:\WorkBuddy\Uninstall WorkBuddy.exe" /allusers`
→ `D:\WorkBuddy`），这条对「打开安装目录」和跨来源去重都关键。

目录扫描有 8 秒总预算（`_FOLDER_BUDGET`），机械盘上大目录 walk 超时就带着已有结果返回，
不能让进度条干等。扫描仍整体跑在任务中心线程里，进度分段：注册表 15% → 目录 55% → 整理 90%。

32/64 位视图用 `KEY_WOW64_64KEY` / `KEY_WOW64_32KEY` 显式指定，不再依赖
`WOW6432Node` 路径——后者只在 64 位 Python 下成立，32 位进程会被系统重定向，
结果是 64 位软件全丢、32 位读两遍。

## 六、关键设计决策

写代码前先看这一节，很多「为什么这么写」都在这里。

### 6.1 页面不持有业务数据

早期每个页面自己扫、自己存，导致体检页要重新扫一遍才能用清理页的数据，
而且同一份数据在不同页面显示的数字还不一样。

现在统一走 `store`。**新增页面请订阅 store，不要自己存扫描结果。**

### 6.2 任务必须串行

并发扫盘不是更快，是更慢 —— 磁盘 IO 争用会让两边都卡住，而且没法及时响应取消。
`TaskCenter` 强制单任务执行，其余排队。

### 6.3 删除类操作必须可回滚

- 文件删除一律走回收站（`trash.recycle`）
- 注册表删除前**强制导出 .reg 备份**，备份失败就取消删除
- 回收站还原时目标已存在则自动加 `(1)` 后缀，**绝不覆盖**

### 6.4 路径保护三道防线

`safety.is_protected()`：无法规范化 → 视为受保护；系统目录前缀 → 保护；
用户主目录根 → 保护。系统级清理项靠 `allow_prefixes` 显式放行。

### 6.5 图标只有一个渲染源

`ui/appicon.py` 的 `render(size)` 是唯一出图入口，窗口图标、托盘图标、
打包用的 .ico 全从它来。改图标只改这一个文件。

`ui/icons.py` 按 `(名字, 颜色)` 缓存 `QSvgRenderer`，所以换肤时必须
`icons.clear_cache()`（`_rebuild_for_theme` 里已接）。不清的话每换一次强调色
就多留一批再也不会用到的渲染器。

### 6.6 只有非管理员才过滤提权项

打包后的程序带 `requireAdministrator`，正常情况不会走到这里。但从源码直接跑
（普通权限）时，一键优化会**过滤掉 `needs_admin` 的规则** —— 否则扫出几百个
文件全都删不掉，用户看到一片「被占用」。

同理，界面上所有「需要管理员权限」的文案都删掉了：管理员是默认状态，写了只会
变成噪音。`Rule.needs_admin` 现在只用于两件事：非管理员时默认不勾选、优化时过滤。

### 6.7 监控页是一个壳

7 个监控视图收进 `MonitorPage`（`ui/pages_monitor.py`），侧栏只剩 1 项，
页内用 `Segmented` 切总览 / CPU / 内存 / 磁盘 / 网络 / 进程。两条硬规则：

- 六个分段第一次切过去才建（`_ensure`），建的时候用 `_last_snap` / `_last_proc`
  补一帧，切进来不会空着。进程表一个人就占几 MB（一屏四百多行的表格项），
  多数人打开只看总览。
- 转发只发给**已经建出来**的子页；它们各自维护趋势缓冲，切回来第一帧就接上。
- 慢读取（磁盘 SMART 要开物理磁盘句柄）放 `_prepare()` 里，首次切到该段才跑，
  不要塞进构造函数，否则启动会卡。
- 内存段左上角那行状态字（「正在优化…」「释放 1.2 GB」）走 `set_memory_status()`：
  内存段还没建时先记在 `_mem_status` 里，建的时候补上。主窗口不要自己去摸
  `monitor.memory`，那个属性现在可能根本还不存在。

主窗口只认 `monitor` 一个 key：`switch_page` 里别再写 `key == "disk"` 这类分支，
分段相关的懒加载一律沉到壳内部。

### 6.8 主题跟随系统，强调色固定品牌色

`Settings` 的默认值是 `theme="system"`、`accent=""`。

|---|---|

### 6.9 垃圾清理页的三条硬规则

`ui/page_clean.py` 重排过一版，改之前先看这三条：

- **每项右侧写「清的是什么」，不写权限**。`Rule.note` 是唯一文案来源，
  空着会退回分类名；左侧行整行可点，点名称/说明/空白都能切换勾选。
- **扫描和删除都在任务中心跑**。删除用 `cleaner.delete_items()`，它会把
  「被占用 + 取消后没轮到的」一起返回：写回 `store` 后列表和体检分数才是真实值。
  不要退回在 UI 线程里 `cleaner.delete()`，几万个文件会卡死窗口。
- **删除时也要按规则放行系统目录**。`scan()` 扫 `C:\Windows\Temp`、
  `SoftwareDistribution\Download` 这类目录时传了 `rule.allow_prefixes`；
  `delete_items()` 必须用同一份清单（`_allow_index()`），否则系统级规则的每个
  文件都会被安全层判成「受保护」，界面表现为「已清理 0 个 · 133 个被占用」，
  而且这些项永远留在清单里，点多少次重试数字都不变。
- **已经不在的文件别再留在 `remaining` 里**。`is_protected()` 走
  `realpath(strict=True)`，路径不存在时直接返回「保护」，这些项会变成永远
  删不掉的僵尸项。删除前先 `os.path.lexists()`，不在的算已清理（不计 `freed`）。
- **重试不再弹确认框**。`_confirm_clean(ask=...)`：第一次「立即清理」确认一次，
  之后点「重试剩余 N 个」直接执行，否则每点一次都弹窗，像按钮坏了。
- **剩下删不掉时要说出「是谁占着」，不能只给一个「重试」**。清理完成后如果还有
  剩余项，页面会起一个 `junk_locks` 任务调 `filelock.lockers()`（Restart Manager
  查占用），查到就把主按钮换成「关闭 Chrome 并清理」，次按钮留「直接重试」。
  只给重试的话，用户不知道该关什么，点几次结果都一样 —— 这正是这个功能存在的理由。
  - 关程序分两步：先 `PostMessage(WM_CLOSE)` 让程序正常退出（浏览器会落盘），
    2.5 秒后还在的按进程树强杀。浏览器缓存常由渲染进程持有，所以要顺着同名 exe
    的父链找到主进程整棵树一起关，只关子进程主进程会立刻写回来。
  - `explorer.exe` / `svchost.exe` 这类系统进程**不关**（关掉 explorer 任务栏会没），
    `Holder.closable=False`，界面只说明「属于系统程序、不会自动关；重启电脑后再试」。
  - 查占用是后台任务，按钮文案在结果回来之前保持「重试剩余 N 个」，不要做
    「检查占用…」这种中间态：查询排在别的任务后面时，按钮会长时间既不能点又没反应。
- **后加的控件要手动 `show()`，清理旧行要先 `setParent(None)`**。父卡片已经
  显示出来时，`addWidget` 不会自动把新控件显示出来；只 `deleteLater()` 的话
  旧分类行要等事件循环才消失，下一帧新旧会叠在一起。
- 空态/结果态的切换靠 `_pending_done`：只在「清理任务刚把结果写回 store」的
  那一次渲染显示「已释放」，别的地方触发扫描不会残留上一条结果。

### 6.10 大文件页：扫描范围、类型、勾选删除

用户要的是「能按格式挑着删」。四条约束决定了实现：

- **「扫描类型」和筛选条不是一回事**。工具栏的类型下拉会真的改变扫描范围
  （`scan_ex(kinds=[...])` 先按扩展名过滤再 `stat`，全盘 2.6 万个文件 0.6 秒），
  筛选条只在已有结果里切着看。所以按「视频」扫完，其余胶囊会置灰并写明本次没扫。
- **切类型要连带调低阈值**。`KIND_MIN_MB` 给每类一个建议值（视频 30 MB、
  安装包 5 MB…），否则拿 200 MB 的默认门槛扫「视频」，短片全被筛掉，
  用户会以为功能没生效。用户之后手动改阈值不受影响。
- **`.exe` 只在「安装包」类型下按文件名认**。全盘扫 `*.exe` 出来的是
  `WorkBuddy.exe`、`node.exe` 这些程序本体，用户差点把自己的软件删了。
  `_looks_installer()` 只留名字带 setup/install/安装/更新/patch/升级 的，
  且排除 uninstall/unins（那是卸载器）。`msi`/`iso`/`wim`/`appx` 不受此限。
- **类型只在渲染时算，不进 store**。`BigFile.category` 是 `path` 的后缀推导，
  扫描只存 `(path, size, mtime)`；改分类规则不需要重扫，改完刷新就生效。
- **筛选是纯前端过滤**。切筛选只重排 `_rows`，不发任务、不重扫。
  筛选条上的数字来自 `bigfile.summarize()`，tooltip 里带各类合计体积。
- **排序自己实现**。`QTableWidget.setSortingEnabled` 会重排表格行而 `_rows`
  不动，勾选立刻错行；这里点表头只排 `_rows` 然后重填，勾选按路径走不会错。
  排序状态显示在底部（`按大小 · 降序`），**不要塞进表头** —— 中文字体下
  `↓` 会掉到基线以下，看着像多出一个符号。
- **勾选状态按路径存**（`_checked: set[str]`），不绑行号。切筛选、换排序、
  删除后重渲染都不会丢；`itemChanged` 里必须用 `_filling` 挡住填充期的递归回调。
- **删除走任务中心 + 回收站**。`bigfile.delete_to_trash()` 每批 100 个，
  送完一批用 `os.path.exists` 逐个复查 —— `SHFileOperationW` 只返回批次总数，
  不告诉你是哪一个失败，只有复查才能把「剩下的」准确还给界面。
- **删除后只更新 store，不重扫**：`store.set_bigfile_files(remaining)` 会沿用
  上一次的 `kinds` / `min_size`，所以删完仍是「视频 + 30 MB」而不是跳回全部类型。
- **结果上限 800 条**（`LIMIT`），按体积取前 N；真被截断时状态栏会写
  「结果已截到体积最大的 800 个」，不要让用户以为只有这么多。
- **默认范围是「系统盘」，不是用户目录**。单分区机器上 `C://Users//xxx` 之外
  才算大头（游戏、下载、Program Files），默认扫用户目录等于什么都没扫到。
  Windows 目录仍在 `SKIP_DIR_NAMES` 里跳过（那部分由磁盘空间页和系统瘦身负责）。
- **系统文件标灰不可勾**：`hiberfil.sys` / `pagefile.sys` 这类扫得出来但删不得，
  名字后面直接写「（系统文件）」，别指望用户去分辨复选框禁没禁用。
- **云盘占位文件不列**：OneDrive「按需」的文件逻辑大小几十 GB、本地 0 字节。
- **空结果用盖在表格上的 QLabel**（`self.empty`）。类型扫描本来就经常没结果，
  一张空白表格看着像没加载。它设了 `WA_TransparentForMouseEvents`，不会挡
  右键菜单；位置在 `resizeEvent` 里按「表头高度以下」重算，别写死坐标。

### 6.11 顶部「可释放 X」是一个跨页汇总，不是某个页面的数字

用户反馈过「这 4.9 GB 是什么，好像不能清理」。查下来是三个问题叠在一起：

- **数字是两处相加**：`reclaimable = junk.total + dup.wasted`。用户那次
  4.9 GB 里，垃圾只有几十 MB，其余全是重复文件。
- **点击一律跳垃圾清理页**：跳过去看到的是一张几乎空的清理页，
  于是结论只能是「这数字清不掉」。现在 `store.reclaimable_parts()` 返回分项，
  点按钮弹菜单（垃圾文件 / 重复文件，各带体积和扫描时间），点哪项去哪页；
  只有一类时直接跳。按钮文字加 `▾`，tooltip 写完整明细。
- **清完数字不动**：页面清理走的是 `store.set_junk_items()` / `set_dup_groups()`，
  不经过 `store.apply()`，而顶部只在 `apply()` 之后刷新。现在 `MainWindow`
  直接订阅 `junk_changed` / `dup_changed`。

另外两条容易忘的：

- **重复文件清理必须写回 store**（`set_dup_groups`）。原来只改页面自己的
  `_groups`，结果是送完回收站顶部数字不减，换肤重建后这些文件又从 store
  里冒出来。写完 store 会重填表格并覆盖统计文案，结果提示要在写回之后再 `setText`。
- **一键优化不碰重复文件**（删错找不回来，要用户确认），所以优化完顶部可能还
  挂着几 GB。`_on_optimized` 现在会明说「还有 X 重复文件待确认」，建议弹窗里
  多一个「去看重复文件」按钮，别让用户自己去猜入口在哪。

「可释放」跟着 `NO_OPTIMIZE_PAGES` 一起隐藏是旧逻辑：在清理页/重复文件页看不到
它，用户就没法知道另一半在别的页面。现在由 `RECLAIM_HIDDEN_PAGES`
（设置/软件/系统信息/体检）单独控制，其余页面都显示。

扫描范围预设见 `bigfile.PRESETS`，`drives` 用 `GetLogicalDrives` + `DRIVE_FIXED`
只取固定盘；`_pick_dir()` 选完目录会把下拉框切到「选择目录…」，取消则回退到上一个预设。

### 6.12 一件事只留一份实现

三个最容易分叉的地方，新增代码时不要再抄一份：

- **字节格式化**：唯一实现是 `winmem.fmt_size()`（GB 两位小数、MB/KB 取整、
  小于 1 KB 给 B）。`metrics.fmt_bytes` 只是保留旧名字的转发（页面代码都在用它）；
  原来 `sysinfo` 还有一份同名转发，已经删掉，系统信息页直接 import 唯一实现。
  以前四个模块各写一份，同一个文件在不同页面能显示成 1.2 GB 和 1.23 GB。
- **Windows 路径常识**：`winpath.system_drive() / home_roots() / documents() /
  fixed_drives() / hive()`。系统盘曾在 `metrics`、`slim` 各写一遍，文档目录在
  `appclean`、`social` 各写一遍，固定磁盘在 `apps`、`bigfile` 各写一遍 ——
  其中 `apps` 那份漏了 try/except，插着空读卡器时 GetDriveTypeW 抛异常会让整次
  软件扫描失败。新增页面别再自己拼 `os.environ["SystemDrive"]`。
- **喂一帧数据**：`ui/feed.py: feed(page, snap, proc)`。页面按需创建，建出来到下次
  采样之间是空的，主窗口建页、主窗口切页、监控页建分段三处原来各写一遍
  `getattr(page, "update_metrics", None)`。
- **取消一组任务**：`TaskCenter.cancel_many(*ids)`。`cancel()` 对「没在跑」返回
  False 且无副作用，所以页面 `shutdown()` 不需要先 `is_busy()` 再 `cancel()`，
  十个页面原来都写了这个两步判断。
- **表格外观**：`components.make_table(headers, ...)` 收敛「无网格、整行选中、
  不可编辑、表头样式」这些处处相同的部分。列宽和拉伸模式差异太大，仍由各页自设。
  七个页面原来各抄一份十余行，改一处样式要改七遍。
- **清理规则**：`cleaner.builtin_rules()` 带 `lru_cache`。规则只依赖环境变量，
  `rule_summary()` 每渲染一次列表就调一次，不缓存等于反复探社交缓存目录。
- **剪贴板与资源管理器定位**：`components.copy_text()` / `components.reveal_file()`。
  四个页面的右键菜单都要「复制名称/路径」和「打开文件位置」，原来各写一份，
  连 `QApplication` 都在函数体里再 import 一次。定位函数还多一步：文件已经
  不在时退回到父目录，否则 explorer 会弹一个空窗口。

反过来，**不要为了「统一」抽基类**：各页的 `_on_task_progress/finished/cancelled`
看着一样，但每页在回调里做的事都不同（有的写 store、有的只改按钮），抽出去只会
让「这页到底做了什么」更难读。

### 6.13 顶部动作：一屏只留一个实心蓝

用户截过一张图说「这几个显示真丑」：顶部 `可释放 X · 去清理 ▾ / 强力模式 / 一键优化`
一行，紧跟着页面自己的 `导出备份 / 删除选中 / 扫描注册表` 一行，两行按钮都靠右、
都拿实心蓝收尾，右边缘对齐成一列，看着像表格里的两列按钮。

现在按「层级」而不是「位置」来排：

- **窗口级动作留在标题行**（`可释放 X ▾` + 竖线 + `强力模式` + `一键优化`）。
  `可释放` 和动作之间加一根 15px 竖线：左边是状态，右边是动作。
- **`一键优化` 改用 `#Tonal`**（淡强调色底 + 深一档的强调色字）。页面自己的
  主动作（扫描/清理/重新扫描）才是这一屏唯一的实心蓝；两个实心蓝并排，
  谁也说不清哪个更重要。淡底文字色用 `mix(ACCENT, TEXT, 0.30)`，
  直接用 ACCENT 只有 3.7:1，压不住。
- **页面动作放进卡片内部**（`card.body().addLayout(bar)`），只改了三页
  （注册表/计划任务/回收站）—— 其余页的工具条本来就在卡片里。按钮进了卡片，
  右边距多出卡片边框 + 10px 内边距，不再和标题行的一列对齐。
- **禁用态主按钮走灰**（`PANEL_SUNKEN`），不要用 `ACCENT_SOFT`：淡蓝现在已经
  专门表示「可点的全局动作」，两者撞色会让人以为按钮还能点。
- **竖线跟着动作组一起藏**。`settings/software/sysinfo/health/clean/dup/bigfile/startup`
  属于 `NO_OPTIMIZE_PAGES`，这些页只剩一个「可释放」，留一根垂线挂在右上角很难看。

改完顺手统一了三页的表头：它们手写 `QTableWidget`，没设 `setDefaultAlignment`，
表头默认居中、单元格左对齐，和用 `make_table` 的其它页不一致。

### 6.14 提示框自己画，别指望 QToolTip 的样式表

用户截图：系统信息页内存条的 tooltip 是纯黑底配深灰字，一个字都读不出来。

排查结论（几条弯路记下来，省得再走）：

- `QToolTip` 是带 ToolTip 标志的独立顶层窗口，它的样式规则是从**触发控件的样式表
  链**上取的。本项目几乎每个 `QLabel` 都在 `setStyleSheet` 里写了 `color:`，全局
  样式表里的 `QToolTip` 规则因此被挡掉，底色回落到系统调色板——Windows 深色模式下
  正好是 `#000000`，字色又是控件样式表里的 `#1A1A1A`，于是黑底黑字。
- **把规则挂到 Root / Card / 触发控件自己身上都没用**（实测同样黑），改
  `QPalette::ToolTipBase` 也没用（QTipLabel 不认应用调色板）。同一个窗口里
  「触发控件没有样式表」时规则是生效的，正是这一点最迷惑人。
- 结论：颜色不可控，那就自己画。`ui/tooltip.py` 里是一个 `QWidget`，
  `paintEvent` 画圆角矩形 + 文字，颜色取 `T.TOAST_BG / T.TEXT / T.BORDER_STRONG`。
- 接管方式：`MainWindow` 上装应用级事件过滤器，`QEvent.ToolTip` 换成
  `Tip.show_text()` 并返回 `True`（不吞掉的话 Qt 还会弹一个黑框）。
- 收起时机：鼠标离锚点超过 8px、按下鼠标、滚轮、按键、窗口失活、12 秒超时。
  8px 是给手抖留的余量，否则轻轻一动提示框就没了。
- 表格单元格的提示挂在 item 的 `ToolTipRole` 上，`QAbstractItemView` 自己会处理；
  过滤器先取 `indexAt(pos).data(ToolTipRole)`，取不到再看控件自身和父链。
- 自绘框**必须** `WA_TranslucentBackground`，否则圆角四个角是方的。
  用 QSS 给这个自绘控件上背景反而不行（透明窗口 + `background-color` 不画），
  直接 `QPainter` 最稳。

### 6.15 体检页下半屏：数据现成，别再空着

11 项明细 + 建议只占半屏，窗口一拉高，下面就是一大片底色（用户截图问
「好大个空白，加点什么」）。补的是**磁盘空间 + 实时负载**两块，数据全部来自
每秒下发的 `MetricsSnapshot`，**不新开任务、不重扫盘**。

几个必须知道的点：

- 页面套了 `QScrollArea`（`widgetResizable=True`）。默认 1100×720 时内容
  701px、视口 639px，滚 62px；拉高到 900+ 时滚动条消失，下排的仪表把余高吃掉。
  没有这层滚动的话，窗口一矮下排就被压成一条线。
- `MeterBlock`（负载）和 `DiskRow`（分区）都是 `Expanding` + **首尾各一个
  `addStretch(1)`**。只写 `Expanding` 不写 stretch 的话，行被拉高时内容会贴在
  顶部、进度条掉到行底，看着像断开的两个东西 —— 这是调这一块花时间最多的地方。
- **不要给这两类行设 `setMaximumHeight` 来「防散」**：限高之后多出来的高度
  只能落在卡片底部，卡片边框会把那片空白框起来，比原来更难看。要么让它长，
  要么别给卡片 `stretch`。
- 分区行按 `mount` 元组比较，**只有挂载点变了才重建行**（插拔移动盘、挂载
  VHD）。每秒重建 4～5 个 `QWidget` 会让布局一直抖。
- 颜色/文本都做了「变了才写」的判断：`setStyleSheet` 每次都重新解析整条声明，
  每秒刷 5 个块没必要。
- 没有 `nvidia-smi` 的机器 `snap.gpu` 是 `None`，显卡块直接 `hide()`，
  不留一个「--」。此时负载卡少一块，靠 `Expanding` 自然补上。

### 6.16 托盘菜单只放「窗口关掉之后还用得上」的动作

窗口关掉就只剩托盘，此时能做的事必须一步到位：

```
显示主窗口（默认项，粗体） / 一键优化 / 清理垃圾…
────  内存 62% · 可释放 960 MB   ← 禁用行，纯信息
────  开机自启动 ✓
────  退出
```

- **没放「设置」「重复文件」「大文件」等入口**：那些都要看列表、勾选、确认，
  从托盘进去等于强制把窗口叫回来，不如先「显示主窗口」。托盘菜单控制在 6 项内。
- 状态行是 `setEnabled(False)` 的普通 `QAction`：禁用态天然不可点，颜色由
  `QMenu::item:disabled` 弱化，不需要自绘。
- **只在 `aboutToShow` 里现算，不在 `on_metrics` 每秒刷**：菜单没打开时改文本没有
  意义，每秒触发一次菜单重排纯属浪费。可释放体积也不缓存 —— 缓存一份很容易和
  顶部按钮对不上。
- `setChecked()` 会发 `toggled`，而 `toggled` 连着写注册表的槽。`aboutToShow` 里
  同步勾选状态必须套 `QSignalBlocker`，否则**用户只是打开菜单就改了开机自启**。
- 自启**以注册表实际值为准**（可能被安全软件或其它工具改过），写成功后回写
  `settings.autostart`，并用 `set_checked_silently()` 同步设置页的 `ToggleSwitch`，
  否则会出现「托盘勾着、设置里关着」。
- 写注册表失败（被拦）时把勾选状态回滚并提示，不能让用户以为开了。

### 6.17 体检结果必须能「就地处理」

原来体检只给结论和一段文字建议：用户看到「重复文件 5.4/8」是橙的，唯一的
动作是左下角「全面体检」—— 再扫一遍，问题还在。现在两处给入口：

- **评分明细行**：不达标（`ratio < 0.7`）且这一项真有处理页面时，行尾出现
  一个蓝色文字按钮「处理」。11 行里通常只有 1～2 行有，视觉上不会被当成一列按钮。
- **优化建议行**：每条建议右侧「去处理」。建议本身是 `Advice(text, page)`，
  `page` 为空就不给按钮（磁盘 SMART 告警、系统盘容量、4K 对齐、休眠文件，
  点进去什么也做不了，给按钮比不给更糟）。

关键约定：

- **阈值只有 0.7 一个**：`build_advice` 的 `low()`、`FactorRow.btn_go` 的显示条件
  都读它。不要另起一个数值，否则会出现「变橙了但没有处理入口」。
- 映射表 `core/health.py::FACTOR_PAGE` 是**因子 → 页面 key** 的唯一来源，
  UI 只查表。`free → bigfile`（空间不够去挑大文件）、`social/upd → clean`。
- 跳转走 `HealthPage.navigate_requested = Signal(str)`，主窗口连 `switch_page`，
  页面自己不碰导航。
- 按钮样式 `#Link` 在 `theme_dark.py`：`min-height: 18px` 是必须的 —— 因子行
  封顶 30px，用 `#Ghost`（26px）会把行撑开或压掉文字。
- **文案不要带 `›`**：`›` 在 10.5px 下渲染成一个点，看着像杂点。就是「处理」
  「去处理」四个字，靠颜色和位置表达可点。

### 6.18 软件专清：按软件拆，不是再做一个垃圾清理

垃圾清理页是「按规则扫全盘」，用户看到的是「社交缓存 3.2 GB」—— 不知道是哪个
软件、清完会丢什么。软件专清（`core/appclean.py` + `ui/page_appclean.py`）反过来：

- 左侧是**软件**（微信 / QQ / 企业微信 / 钉钉 / Chrome / Edge / Firefox），
  只列真的发现了缓存目录的那些；一个都没找到的软件不出现。
- 右侧是当前软件的**类目**（聊天图片 / 视频 / 文件 / 表情 / 程序缓存…），
  每类带一句「删了会怎样」，默认**全部不勾** —— 删掉的是用户真收到过的内容。
- 勾选跨软件保留，底部按钮显示的是所有软件的合计，可以一次清完。

几条不能破的规矩：

- **白名单子目录**，沿用 `social.py` 的思路。`<账号>\FileStorage\Image` 这种才是
  目标，`Msg`、`msg`、`Msg3.0.db` 永远不在名单里。新增软件时先确认目录名，
  别用「排除数据库」这种黑名单思路 —— 新版客户端随便加个目录就漏了。
- **微信 4.x 只认 `FileStorage`**。新版客户端把附件挪到了 `attach/`，结构没验证过，
  宁可不支持也不猜。要加先在本机确认目录内容（有没有 `*.db`）。
- **必须存在账号目录**才认为软件装了：卸载后经常留一个空壳根目录。
- **删除走 `cleaner.delete_items`**，不自己 `os.remove`：路径安全层、占用跳过、
  取消后保留剩余项这些都在那边实现好了。
- 清完把被删路径从 `store.junk` 里摘掉（`PurgeResult.removed_paths`）。垃圾清理页
  的「社交缓存」规则盯的是同一批目录，不同步的话那边会挂着一个早就不存在的体积，
  点「立即清理」清了个寂寞。

界面上两个踩过的点：

- **类目说明必须单独一行**。塞在同一行时被右侧两列数字挤成「删了会重新下…」，
  而这句话正是用户决定勾不勾的依据。行高因此是 46 不是 32。
- **路径按目录截断**，不要按字符掐中间：`…\Google\Chrome\…` 会把 `Google` 切成
  `Go…le`。`_short_path()` 保留盘符 + 末三级目录，长这样：`C:\…\User Data\Default\Cache`。

### 6.19 系统瘦身：改的是策略值，不是删文件

`core/slim.py` + `ui/page_slim.py`。需求是「禁掉系统更新这一类」，但用户的下一句
是「不影响正常运行电脑」—— 所以这一页的取舍全部围绕「可逆 + 说清代价」：

**只做两类事**

| 类型 | 内容 | 怎么回滚 |
|---|---|---|
| 开关（9 项） | 更新自动安装 / 更新后自动重启 / 传递优化 P2P / 遥测服务 / 错误报告 / 商店应用后台 / 搜索网页建议 / 推荐位 / 广告 ID | 删掉写入的值即回系统默认，「恢复默认」一键全改回 |
| 空间（4 项） | 休眠文件 / 旧系统文件 / 内存转储 / 组件存储 | 休眠可重新开启；后三项本身是一次性清理，按钮上标「不可逆」并要求二次确认 |

**不做的**：Defender 实时保护、防火墙、系统还原、页面文件、BITS、搜索索引。
它们省下的资源有限，关掉换来的是另一类问题（安全缺口、蓝屏后无法回滚、内存不足时
直接卡死）。这一条写进了页面底部的说明，别当成漏项。

几个实现上的决定：

- **开关用 `(read, turn_off, turn_on)` 三元组声明**，`turn_on` 是「删值」而不是
  「写 1」：Windows 的偏好值默认值不一定是 1，写死 1 会把用户原来的设置覆盖掉。
- **服务开关先 `sc config start= disabled` 再 `sc stop`**。顺序反了的话，自动启动
  的服务刚停下就被系统拉起来。
- **遥测是两件事**：策略 `AllowTelemetry=0` + 停 `DiagTrack` 服务。只写策略的话，
  服务还在后台跑，任务管理器里看得见，「关了」就没说服力。
- **传递优化写 `DODownloadMode=0`**（只走 HTTP，不做点对点），不是关掉整个服务 ——
  系统更新自己还要下载。
- **空间项体积在任务线程里数**：`Windows.old` 能有十几万文件，UI 线程走一遍会卡。
  数完把体积为 0 的项直接 `hide()`，不留一行「0 B · 已清理」占地方。
- **`HKCU\Software\Policies` 在较新的 Windows 上被锁给管理员了**：普通权限
  `CreateKey` 直接 `WinError 5`。所以「搜索网页建议」以用户级的
  `Search\BingSearchEnabled` 为准，策略能写就顺手写，写不了不算失败 ——
  否则非管理员跑源码时这一项永远失败。
- **每行状态字最少 40px**：9px 字号配 32px 会把「已」裁成半个字（右对齐从左边裁），
  截图放大才看得出来。

**验收脚本** `tools/check_slim.py`：数据层做 HKCU 往返（关 → 读回 False → 开 →
读回 True），非管理员时验证「拒绝且状态不变」；页面层模拟点开关、断言顶部汇总跟着
变、「空间清理」回调把体积和按钮状态复位。**不执行任何真实删除** —— 删休眠文件、
Windows.old 是用户自己的决定。

### 6.20 整体清理：删掉的重复与修掉的逻辑

一轮「别再抄第二份」的收口。删掉的东西都不改变行为，改掉的逻辑都有实测。

**内存泄漏：换肤每换一次漏一整套界面**

`QMainWindow.setCentralWidget()` 不会删除旧的 central widget，只是
`setParent(this) + hide()`。换肤走的正是「重建整个界面」这条路，于是每切一次
主题就留下一整套页面：实测 6 次后 `allWidgets()` 从 1228 涨到 8548，页面对象
从 20 涨到 140。修法是在 `_build_ui()` 里对旧 widget 调 `deleteLater()`。
（`deleteLater` 要等事件循环回收到 DeferredDelete 才真的释放，写测试时得
`sendPostedEvents(None, QEvent.DeferredDelete)` 才看得到回收。）

**懒加载的三份真相合并成一份**

「某页首次进入才加载」原来写在三个地方：`__init__` 里十个 `_xxx_scanned` 布尔、
一个 `LAZY_FLAGS` 元组、`switch_page` 里九段 `if`。加一个页面要改三处，漏掉
第三处就是「换肤后那页空着」。现在只有模块级 `LAZY_STARTERS`（key → 方法名）
和实例上的 `_lazy_done` 集合，重建时 `.clear()` 即可。顺带发现
`_disk_health_loaded` 只在 `LAZY_FLAGS` 里存在、既没初始化也没人读，删了。

**任务失败以前被当成「用户取消」**

`core/task.py` 的 worker 捕获异常后只 `emit(None)`，而 `None` 的语义是「取消了」。
于是扫描崩掉时页面显示「已取消」，用户点几次都一样，日志里只有终端一行。
现在 worker 把错误一起带回来，任务中心新增 `failed(task_id, 描述, 错误)`，
主窗口统一 toast「XX 失败：PermissionError: …」，同时仍然发 `cancelled` 让页面
复位按钮 —— 页面只需要知道「没有结果」，原因由主窗口说。

**退出时不再可能撞上运行中的 QThread**

`_shutdown()` 只停了采样器，没调 `tasks.shutdown()`。页面各自 cancel 的只是
自己的任务，排队中的还挂在队列里，退出时 QThread 正在跑就会
「Destroyed while thread is still running」然后 abort。

**第二次双击图标，窗口真的会被叫到前台**

`single_instance.activate_existing()` 用的是 `FindWindowW(None, "Windows系统管家")`，
而这个 API 要求标题**完全相等** —— 实际标题是「Windows系统管家 v0.0.11·内测」，
永远匹配不上，函数一直返回 False。改成 `EnumWindows` 按前缀找。

**配置写坏不再让程序起不来**

`Settings.load()` 只按字段名过滤，不看类型：`"interval_ms": "1000"` 能进来，
最后崩在 `QTimer.setInterval` 里，用户看到的是「双击没反应」。现在按默认值的
类型逐个归一，类型不对的字段回落到默认值。

**每秒都在重复的样式重算**

`KpiCard.set_value` / `RankList.set_rows` 原来每帧都 `setStyleSheet`，而负载
颜色只在三档之间跳。改成颜色变了才写。同理托盘图标：只有「是否跨过 85%」这
一位会体现在图标的红点上，不必每秒重绘一张 64×64 的图。

**顺手删掉的**

- 11 处未使用的导入（`QComboBox` / `QHeaderView` / `QPainterPath` / `font` …）。
- `TrendChart` 里重复了一遍的类文档字符串（第二个是裸字符串表达式，没有任何作用）。
- `health.HealthReport.suggestions` 兼容属性（改成 `advice` 之后就没人用了，
  注释还写着「主窗口弹窗在用」，实际那个弹窗读的是 `optimize.Report`）。
- `optimize._is_admin()`（内部再 import 一次 winmem，直接调 `winmem.is_admin()`）。
- `main_window` 里的 6 处函数内 `from PySide6... import`（模块顶部已经导入）。
- 4 个一次性预览脚本（`preview.py` / `preview_new.py` / `preview_win11.py` /
  `preview_fill.py`，功能被 `preview_pages/themes` 等覆盖）。
- 根目录 152 张历史截图挪到 `docs/preview/`（脚本可随时重生成）。

**没有做的**：把 11 个页面的 `_on_task_finished/cancelled/progress` 抽成基类。
理由见 6.12 最后一段 —— 每页回调里做的事不同，抽出去只会让「这页到底做了什么」
更难读。省下的几十行不值这个代价。

### 6.21 页面按需创建：启动内存 102 → 73 MB

以前十四页在 `_build_content()` 里一次性造好塞进 `QStackedWidget`：控件一千二百多个，
全局样式表要逐个 polish，光这一步就多占二十多 MB —— 而用户一次只看一页。

现在的分工：

- `_create_page(key)` 按 key 造页面，**模块导入写在分支里**，不打开的页连模块内存
  都不用付（十五个页面模块合计约 10 MB）。
- `_ensure_page(key)` 取页面，没建过就现建；建完立刻用最近一帧 `_snapshot` /
  `_last_proc_rows` 填一次，切进来不会是空白页。
- `switch_page()` 走 `_ensure_page`。`__getattr__` 兜住 `window.page_xxx` 这种写法
  （测试脚本、调试时常用），只在常规属性查不到时触发，不遮蔽真实属性。
- **不要为了改一行字把整页造出来**：`_on_task_cancelled` / `run_optimize` /
  `_refresh_cooldown_text` / `_add_whitelist` / `_tray_toggle_startup` 里全是
  `self._pages.get(...)` + `if ... is not None`；`on_metrics` 只遍历已建出来的页。
- `run_full_check()` 是例外：它会把 clean / dup / registry 三页建出来，因为扫描范围
  （勾选的规则、查重目录）是页面自己的状态，在别处重写一份迟早跟界面上的勾选对不上。
  这三页各不到 1 MB，而且只在用户按下体检时才发生。
- 监控壳内部同理：六个分段第一次切过去才建。它现在还要记住「停在哪一段」
  （`_monitor_segment`），因为换肤重建会把整个壳重造一遍。

实测（同一台机器、同一测量方式）：启动 102 → 73 MB，切到概览 114 → 88 MB；
监控壳第一次建出来 9.8 → 2.3 MB。

回归脚本 `tools/check_startup.py`：断言首屏是体检、主题下拉是「跟随系统（默认）」、
十五个导航项 + 六个分段都能按需建出来、换肤重建后还能建。

### 6.23 分发：zip + 校验和，以及「文件或目录损坏」的真相

用户在另一台机器上双击 exe，Windows 报「文件或目录损坏且无法读取」（0x80070570）。
这类报错**与本项目代码无关**，判断顺序如下：

1. **先比 SHA256**。`releases/vX.Y.Z/SHA256SUMS.txt` 与 `manifest.json` 里都有，
   对不上就是文件在传输 / 下载过程中不完整。
2. **别直接从微信聊天窗口双击**。微信会先把文件落到 `msg\file\...` 缓存目录，
   没下完就是一个残缺文件，双击必然报损坏。先「另存为」到本地目录再运行。
3. **代码层面救不了**。单文件 exe 在 PyInstaller 的 loader 解包阶段就失败，
   我们自己写的任何代码都还没跑起来，做不了友好提示。

打包侧因此加了三样东西：

- `build.py: verify_exe()`：检查 MZ 头、PE 签名、结尾的 PyInstaller 归档 cookie
  （`MEI\014\013\012\013\016`）和体积（< 20 MB 视为异常）。任一项不过就
  **不归档并返回非零**，避免把半截文件发出去。
- `releases.archive()` 多产一份 `Windows系统管家-vX.Y.Z.zip`，内含 exe 和
  `README.txt`（写清 SHA256 期望值、正确用法、「损坏 ≠ 程序坏了」）。
- `README.txt` 之外再写 `SHA256SUMS.txt`；`manifest.json` 增加 `exe_bytes` /
  `exe_sha256` / `zip_sha256` / `zip_mb`。

**zip 不是为了压缩**：exe 内部的库已经是 zlib 压过的，实测 36.6 → 36.3 MB，
几乎压不动。它的价值在 CRC —— 解压报错能直接定位「这个包坏了」，比双击后
一句 0x80070570 清楚得多。

### 6.25 「内存怎么这么高」：待命缓存被少算，缺口全进了「使用中」

用户发来截图：内存页写着「使用中 12.83 GB（81%）」，同一屏「可用内存」却是
11.40 GB，物理内存一共 15.7 GB —— 12.83 + 11.40 = 24.23，比物理内存还多 8.5 GB。
数字自己打自己，说明采集口径有 bug，不是机器真的吃满了。

根因分两层：

1. **`used` 不能用页列表自己减**（v0.0.14）。当时算的是
   `total - free - standby - modified`，而这三个值来自 `NtQuerySystemInformation`
   的 `SystemMemoryListInformation`，需要 `SeProfileSingleProcessPrivilege`。
   特权没启用时内核返回「部分字段有效」：`FreePageCount` 是对的，
   `PageCountByPriority`（待命）只回来一小截。那一帧待命只报了 2.91 GB，真实约
   11.4 GB，缺的 8.5 GB 全被算成「使用中」，占用率从 28% 虚高到 81%。
   修法：`used = total - avail`，avail 是 `GlobalMemoryStatusEx` 给的权威值，
   和任务管理器的「使用中」同源（已在 `6.x` 那次「改用系统权威口径」的提交里落地）。
2. **待命 / 空闲 / 已修改这三个细分值仍会少算**，构成图里待命那块被画得特别窄，
   四个数字加起来不等于物理内存。修法见 `core/winmem.py: _align()`：
   `avail = 空闲 + 待命 + 已修改`，所以用 avail 反推待命（`implied = avail - free -
   modified`，比页列表大就采信它），再按总量夹一次。不用去抢特权，也不用改注册表。

自检：`tools/check_mem.py` 锁两件事 —— 真机读数必须 `used + avail == total`
且四项和等于物理内存（2% 容差，采集不是原子的）；再用截图那一帧的数值构造用例，
断言 `_align()` 能把 2.91 GB 的待命补到 11.4 GB。

顺带说明「内存使用率」那条曲线为什么是 V 字：一键优化把各进程工作集清掉 → 使用中
瞬间掉到 62% → Windows 在几十秒内把文件缓存重新填满待命列表 → 回到 82%。这是缓存
该有的行为，不是泄漏。「疑似泄漏」面板显示未发现异常增长，也是一致的结论。

**排查真·内存高的正确顺序**：先看「使用中」是不是 `total - avail`（口径对不对），
再看「内存占用 Top」按体积排序，最后才怀疑泄漏 —— 顺序反了容易把缓存当泄漏。

### 6.26 每核占用：竖柱改方块，核数只说一次

用户截图里四根柱子被拉到跟卡片一样高，一大片空轨道，读数只有一个核在跳；
同时「4 物理 / 4 逻辑」在每核卡右上角和 KPI 卡副标题里各说了一遍。

**显示模式**（四个候选渲染成一页对比图，用户选了 A）：

| 方案 | 形态 | 适用 |
|---|---|---|
| **A 方块热力（已采用）** | 每核一块方砖，底色深浅即负载 | 4 核不空旷，32 线程折行放得下 |
| B 横条列表 | 每核一行细条 + 百分比 | 读数最准，但纵向吃高度 |
| C 竖柱改良 | 压矮、平均虚线、只标峰值 | 改动最小 |
| D 圆环 | 每核一个环 | 视觉最轻，核多时环太小 |

`components.CoreBars` 换成 `CoreTiles`（`CoreBars` 已删，全项目只有概览与 CPU 两处
引用）。三个实现要点：

- **列数按「格子接近正方形」自动选**，不是固定一排。4 核 → 2×2、8 核 → 3×3、
  16 核 → 4×4；评分里对「留空格子」加惩罚（`empty * 0.45`），否则 4 核会被排成
  3 列、右下角空一块，看着像少画一个核。
- **热力走开方映射**（`alpha = 28 + 118 * sqrt(load/100)`）。日常负载都在 10~30%，
  线性映射下四块颜色几乎一样；开方把低负载段拉开。上限压住是为了文字对比度 ——
  满载时不能糊成一片色块。
- **砖块够大（≥54px）才写字**：左上「核 N」、中间百分比；小到只剩色块时用底部

**核数去重**：每核卡右上角改成 `平均 xx% · 峰值 xx%`（`_core_note()`），核数只在
一个地方 —— 概览页是 KPI「CPU」副标题（`_core_text()`：有超线程写「4 核 8 线程」，
否则写「4 核」），CPU 页是「核心」KPI 卡（副标题在有超线程时写物理核数，否则
「无超线程」）。

`tools/preview_core_modes.py` 是一次性的方案对比脚本（四种画法 + 4 核 / 16 线程 /
紧凑版三档），选定后已删除，渲染图留在 `docs/preview/preview_core_modes_*.png`。

### 6.27 总览改版：每核只留 CPU 段，右列换成内存构成 + 系统概况

用户第二次提同一件事：「这个不是这两个还是同时显示」—— 截图是 总览/CPU 分段栏 +
每核占用卡片。6.26 只去了重（核数文字），**控件本身**还在两个分段里各摆一份，
打开总览看到四块方砖，切到 CPU 又看到同一张，等于同一块内容看两遍。

**处理**：`每核占用` 只保留在 CPU 段（它本来就是「哪几个核在忙」的详情），总览腾出来
的位置换两块总览才有意义的信息：

| 位置 | 改前 | 改后 |
|---|---|---|
| 左 2/3 | CPU 趋势（单序列） | 系统趋势（CPU + 内存双序列，共用百分比纵轴） |
| 右 1/3 上 | 每核占用（挪走） | 内存构成：堆叠条 + 使用中/待命/空闲三列数值 |
| 右 1/3 下 | — | 系统概况：开机时长 / 进程·线程 / 本机 IP / 系统版本 |
| KPI | 只有数字 | 数字下加一条按占用比例着色的细线（`KpiCard.set_value(meter=…)`） |

三个实现要点：

- **内存构成横排三列，不是内存页那种竖排图例**。右列只有 270px，竖排三条会把卡片
  撑高；横排三列（`使用中 / 待命 / 空闲` 各一列）既省高度，也和内存页的版式区分开，
  切过去不像在看同一张卡。
- **KPI 细线只在有比例的时候画**（CPU/内存/磁盘给 0~1，网络不给），画法是
  `KpiCard.paintEvent` 里按 8px 圆角裁一块 3px 高的条，跨过 1% 才 `update()`，
  不会每秒重绘四张卡。
- **趋势图双序列时的两处调整**：底色 alpha 56 → 22、渐变高度 0.55 → 0.34（两条
  曲线各铺一大片会把图变成拼色块）；纵轴上限改成「百分比按 10 的整数倍、
  其余按 1/1.5/2/2.5/3/4/5/6/8 取整」（`_nice_ceiling`），刻度不再出现 1523 KB/s
  这种数字；多序列时 `top_pad` 8 → 18，图例有自己的一条带子，不压绘图区。

系统概况里的四行都是「本地算得出来、不用起进程」的：开机时长来自
`psutil.boot_time()`（构造时读一次），进程/线程数来自 `winmem` 的
`SystemMemoryListInformation`（`MemSnapshot` 里本来就有，不用另采），系统版本读注册表。
整组文案不变就不写控件（`_sys_rows` 比对），开机时长一分钟才变一次，不需要每秒刷。

`tools/preview_overview.py` 出三张图（浅色 1100×720 / 深色 / 最小窗口 980×640），
`check_startup.py` 加了一条断言：总览里不允许再出现 `CoreTiles`，CPU 段必须有。

### 6.28 去重：先证明没有死函数，再收拾复制粘贴

「有没有多余代码」这件事得先量。做法是写个一次性 AST 脚本：收集全部顶层函数 /
类 / 方法名，统计它们在**全项目**（含 `tools/`）里出现的次数，等于 1 的才是真没人
用。结果只有 `ShareDelegate.paint` 一项，而它是 Qt 的虚函数回调 —— **死函数一个都
没有**。真正浪费的是同一段代码被抄了好几份：

| 重复项 | 份数 | 收口方式 |
|---|---|---|
| `MainWindow._build_toast` / `_live_tip` | 各 2 份，逐字节相同 | 删掉后一份（前者被后者覆盖，一直没被发现） |
| `enterEvent` / `leaveEvent`（悬停置位） | 6 处 | `components.HoverMixin`，六个控件改成 `class X(HoverMixin, QWidget)` |
| `_system_drive` | `metrics` / `slim` | 新建 `core/winpath.py` |
| `_documents` | `appclean` / `social` | 同上 |
| `_fixed_drives` | `apps` / `bigfile`（后者多了 try/except） | 同上，统一用带保护的版本 |
| `default_roots` | `bigfile` / `dup`（都是 `[str(Path.home())]`） | 同上 → `winpath.home_roots()` |
| `_hive` | `slim` / `startup`（后者还缓存了两个常量） | 同上 → `winpath.hive()` |
| 「拿最近一帧喂给新页面」 | 主窗口建页 / 主窗口切页 / 监控页建分段 | 新建 `ui/feed.py` 的 `feed(page, snap, proc)` |
| `if is_busy(id): cancel(id)` 的循环 | 10 个页面的 `shutdown()` | `TaskCenter.cancel_many(*ids)`（`cancel` 本来就对「没在跑」返回 False） |
| `CoreTiles.compact` | 参数从未被传 `True` | 连同 25 行紧凑版布局一起删 |

两个顺手修掉的问题：

- **`switch_page` 重复喂帧**：`_ensure_page` 刚建完喂一次，`switch_page` 紧接着又喂
  一次，进程页等于一次切页重建两遍四百行表格。现在记住「切之前这一页在不在」，
  只给「停在后台好几分钟」的那种补一帧。
- **退出时刷一串 `Internal C++ object already deleted`**：全局事件过滤器挂在
  `QApplication` 上，比窗口活得久，析构阶段仍在往半销毁的控件投递事件。`_shutdown()`
  开头 `removeEventFilter(self)` 之后，预览/自检脚本退出干净了。

`core/winpath.py` 只放「路径常识」，不做存在性判断（装没装由调用方 `os.path.isdir`
决定）—— 原来的实现里就有把「路径拼好了」当成「装好了」的隐患。

### 6.29 磁盘空间：从「列大文件」到「空间去哪了」

起因是一类机器：整机 / 笔记本出厂就是**一块硬盘一个分区**，系统、软件、个人文件
全在 C 盘。这种机器上「扫 C 盘」等于「扫全盘」，而原来的大文件页在三处正好失效：
默认范围是用户目录（`C://Users//xxx`，装在 `C://Games`、`C://Program Files` 的看不见）、
只有文件清单没有目录聚合（碎文件多的目录永远不出现）、`SKIP_DIR_NAMES` 把 `windows`
整个跳过（Windows 常占 20~40 GB，界面上却是空白）。

于是把「大文件」升级成「磁盘空间」，两个分段：**空间分析**（新增）和 **大文件**（原页
保留）。分析段三段：空间去向堆叠条、可下钻的目录占用、可回收清单。

**遍历方式换掉，先看实测**（本机 C 盘 115 GB / 已用 44 GB / 39 万文件）：

| 写法 | 用时 | 扫到文件 | 统计体积 |
|---|---|---|---|
| `os.walk` + `os.stat`（原 `bigfile.scan_ex`） | 47.9 s | 35.3 万 | 34.6 GB |
| `os.scandir` + `entry.stat()`（新 `dirstat`） | 40.6 s | 39.4 万 | 44.6 GB |
| 同上，文件系统缓存已热 | 12.5 s | 39.4 万 | 44.2 GB |

快 15% 是次要的，**多扫到 4 万个文件、10 GB 才是关键**：`os.stat` 走
`GetFileAttributesEx`，受保护文件直接拒绝访问；而 `FindFirstFile` 枚举目录时已经把
大小一起返回了，用这份数据就不会漏。设备管理器里查不到的文件在资源管理器里看得见，
原因也是这个。

其余几条实现决定，每条都对应一个踩过的坑：

- **目录体积用递归返回值逐层相加**，不做「事后按路径深度合并」。后者试过：
  `C://Users` 9.81 GB 被算成 0.29 GB，因为「按深度倒序合并父子」的边界条件写不对，
  很容易漏掉中间层。
- **跳过 reparse point**（`st_file_attributes & 0x400`）。否则 `C://Users//All Users`
  和 `C://Documents and Settings` 会带着扫描器绕圈。
- **硬链接按 `(st_dev, st_ino)` 去重**，但只对 ≥ 1 MB 的文件做。39 万个 inode 全记下来
  要多花 40 MB 内存，而硬链接几乎都在 WinSxS（本来就不进去）。
- **云端占位文件不计入体积**（`RECALL_ON_DATA_ACCESS` / `ON_OPEN` / `OFFLINE`）。
  OneDrive「按需」文件的逻辑大小几十 GB、本地 0 字节，算进去就是纯误导。它们单独
  计数，界面写「另有 X GB 在云端（不占本地）」。
- **根目录散落的文件并成一行**。本机 `C://` 上躺着 `hiberfil.sys` / `pagefile.sys` /
  `swapfile.sys` / `DumpStack.log.tmp` 四个文件，不合并就吃掉列表四行，把真正的目录
  挤到下面 —— 而目录才是这页要回答的问题。合并项自己带 `children`，点开还是能看到
  具体是哪些文件。
- **只建两层的节点，更深的按需再扫**。`depth=2` 时节点总数 57 个、内存增量 0.5 MB；
  缓存整棵树的话 39 万个节点至少几十 MB。点进第三层才起一个 `space_sub` 任务，
  单目录扫描几百毫秒。
- **并行度按介质类型选**（`dirstat.workers_for()`）：SSD 4 路，机械盘 1 路。
  机械盘上并行只会让磁头来回跑，反而更慢。
- **边扫边出结果**：`TaskCenter.partial` 信号把「刚扫完的那个顶层目录」发回主线程
  （Qt 跨线程信号自动排队），界面收到一行就先画一行。用户 2 秒内就能看到
  `C://Windows` 出现，而不是盯着进度条等两分钟。

**可回收清单刻意不重复清理页已有的项**（更新缓存、传递优化、日志、社交缓存）。
同一笔体积在两个页面算出不同的数，用户只会得出「你们自己都对不上」的结论。这里
只放清理页覆盖不到的大块占用：休眠文件、页面文件、还原点、组件存储、搜索索引、
安装缓存、商店应用、WSL/Docker 虚拟磁盘、回收站。

其中三项**只统计、不给动作按钮**：`Windows\Installer`（删了软件无法卸载/修复）、
`System Volume Information`（还原点全废）、WinSxS 内部。给数字是为了让用户知道
空间在哪，不是让他点。

**「不可勾选」不能用 `safety.is_protected`。** 它把整个 `Program Files` 和 `Windows`
都算受保护（对删除是对的），拿它当「标灰」会让系统盘范围扫出来的**每一行**都变灰。
所以 `bigfile.is_system_file()` 只看文件名（hiberfil / pagefile / swapfile /
memory.dmp / bootmgr），列表里写成「`hiberfil.sys`（系统文件）」——
只把复选框禁掉没用，Qt 的勾选框禁用了还是那个方框，用户看不出区别。

**空间变化**（`core/spacehistory.py`）只存顶层目录的体积，一份快照几百字节。同一天
连着扫几次只留最后一份，但隔了 2 小时以上另记一笔 —— 否则「上午扫过、晚上再扫」
看不出当天谁在长。120 天裁剪、最多 400 条。

体检测评里的系统盘项本来就已经是「百分比与绝对 GB 取较差者」，这次只补了单分区
识别（`partition_count`）：1 个分区时详情写「（仅 1 个分区）」，剩余不足的建议文案
也从「把缓存迁到其他盘」改成「没有第二个盘可以迁，去看磁盘空间」—— 单分区机器上
前一句是句废话。

### 6.30 激活时间：系统里根本没有这个字段

系统信息页加了一张「激活与授权」卡，六项：激活状态、激活方式、系统激活时间、
硬件激活时间、产品密钥、产品 ID。做起来才发现，「激活时间」在 Windows 里**没有任何
权威字段**，只能靠痕迹推定，所以每一条都要在 tooltip 里交代来源。

**能直接读的：`slmgr.vbs /dlv`，而且不需要管理员。** 实测 1.5 秒、返回 695 字节，
拿到许可证状态、`产品密钥通道: OEM:DM`、部分密钥、激活 ID。这条路能走通是关键 ——
另一条路 WMI（`SoftwareLicensingProduct`）本项目一律不用，而注册表里没有状态值。
但 `/dlv` **不给激活时间**，只有「信任时间」（最近一次校验，每次开机都变）。

**时间只能从痕迹推。** 本机（2026-11-06 装的系统，出厂镜像 2019-12）实测三条：

| 痕迹 | 时间 | 判断 |
|---|---|---|
| `spp\store\2.0\tokens.dat` 创建时间 | 2026-11-06 10:43 | 采用 —— 安装（10:42）后 1 分钟，正是 OEM DM 自动激活 |
| `ClipSVC\Archive\KeyHolder\*.xml` 创建时间 | 2026-11-06 18:52 | 弃用 —— 打开看 XML 里的 `IssuedDate` 是 2017-10-04，那是**微软签发 OEM 密钥**的日子，不是激活 |
| `SYSTEM\Setup\CloneTag` | 2019-12-07 09:18 (UTC) | 采用为硬件侧 —— OEM 出厂 sysprep 封装时间 |

所以：**系统激活时间 = `tokens.dat` 的创建时间**，**硬件激活时间 = `CloneTag`**
（读不到时退回 `ClipSVC\Install\Apps` 目录的创建时间，本机是 2019-12-07 22:47）。

- 用 `tokens.dat` 的 **ctime** 而不是 mtime：每次联网校验都会重写这个文件（本机
  mtime 是 11-08），ctime 只在文件被新建时记录，日常校验不会把激活时间刷成今天。
- `CloneTag` 是 **UTC** 字符串，`time.strftime` 直接解析成 struct_time 会当成当地时间，
  差 8 小时（17:18 会显示成 09:18）。要先 `calendar.timegm` 再 `localtime`。
- 界面只显示日期不显示时分，因为两个出厂痕迹差了 5 个多小时（封装 17:18、
  落盘 22:47），显示到分钟反而像矛盾。系统激活时间显示到分钟，因为它和安装日期
  是同一天，只写日期会看着像重复项。

**1.5 秒不能放主线程。** 也不该走 `TaskCenter` —— 那是串行队列，前面压着一个五分钟
的磁盘扫描时，打开系统信息页会干等几分钟。这里用普通 `threading.Thread(daemon)` +
页面上的 `Signal(object)`，槽在主线程收（Qt 跨线程信号自动排队）。不用 `QThread`：
换肤会重建页面，`QThread` 在运行中被析构会崩，而 Python 线程不是 QObject，页面没了
信号自然没人接，不需要写 `shutdown()`。模块里另加 10 分钟缓存，换肤重建不重复起进程。

其余几条：

- **中文机器的 `cscript` 输出是 GBK。** 想用 `//U` 强转 UTF-16 会掉坑：那个开关依赖
  控制台，配合 `CREATE_NO_WINDOW` 之后 stdout 直接是 0 字节。只能按代码页解码，
  顺序 `utf-8 → mbcs → gbk`（GBK 高位字节不是合法 UTF-8 起始字节，不会误判）。
- **字段名本地化**，中英两套白名单都认；第三国语言认不出来时，退回正则从全文捞
  `OEM:DM` / `Retail` / `Volume:MAK`，状态则原样显示不硬译。
- **`产品密钥通道: OEM:DM` 的值里还有冒号**，所以只按**第一个**冒号切行。
- **`InfoRow` 的标签宽度原来写死 76px**（四个字），「系统激活时间」六个字会被截。
  加了 `width` 参数，这张卡传 96。
- `sysinfo._reg` 提升为公开 `reg`，`activation.py` 直接复用，不另抄一份注册表读取。
- 七张卡在默认窗口（1100×720）放不下一屏，激活卡放在第三行通铺，打开时正好露出
  卡片标题和第一行，往下滚能看到全部 —— 没有为了塞进去砍掉 产品密钥 / 产品 ID，
  这两项重装系统时是要用的。

没做：查微软服务器上的数字许可证绑定时间（要联网 + 微软账号，且只对数字许可证有效）。

### 6.31 硬件生产日期：SMBIOS 里根本没有这个字段

用户接着问「能不能拿到内存、主板、CPU 的生产日期和激活时间」。把本机整张 SMBIOS 表
（3025 字节）逐条解出来，答案是：**拿不到，而且不是我们没读全，是规范里就没有**。

| 设备 | SMBIOS 里实际有的字符串 |
|---|---|
| 内存 Type 17 | `DIMM CHA1` · `BANK 0` · `04CB` · `B1000000` · `9876543210` · 空 |
| CPU Type 4 | `CPU1` · `Intel(R) Corporation` · `i3-9100T @ 3.10GHz` · 空 · 空 · 空 |
| 主板 Type 2 | `FUJITSU` · `D3603-A1` · `S26361-D3603-A1` · `98043498` · 空 · 空 |

整张表里**唯一带日期的字段只有 BIOS 的 ReleaseDate**。内存那两个值是主板厂填的占位
（序列号 `B1000000`、资产标签 `9876543210`），CPU 的 Serial/Asset/Part 三个字段干脆是
空串（Intel 消费级 CPU 本来就不提供序列号）。

硬件层面的真相：

- **内存条其实有生产周次**，写在 SPD EEPROM 的 byte 32–33（JEDEC 规定，年/周编码）。
  但它挂在 SMBus 上，用户态没有驱动读不到 —— AIDA64 那类工具是装了内核驱动才拿到的。
  为了一个日期装驱动，不做。
- **CPU 有 FPO/Batch 批号**（顶盖钢印，形如 `X933B123`），纯物理标记，软件不可见。
- **主板没有生产日期**，只有序列号 + BIOS 日期。BIOS 日期是固件发布日，只能当批次下界
  （本机 2019-07-04，整机 2019-12 出厂，差 5 个月，合理）。
- **「硬件激活时间」不存在这个概念**，激活只发生在软件许可上。

所以改做能做的三件事：序列号全部摆出来（查保修用）、加一张存储设备卡、把硬盘通电
小时数读出来 —— 后者是「这台机器实际用了多久」唯一可靠的硬件信号。

**通电时间：绕了三圈才走通，最后破例用了 PowerShell。** 过程记下来，省得下次再试：

1. `IOCTL_SMART_RCV_DRIVE_DATA`（ATA SMART 直通）—— 本机两块 SATA 盘都返回 **err 5**；
2. NVMe 的 SMART 日志页（`IOCTL_STORAGE_QUERY_PROPERTY` + `StorageDeviceProtocolSpecificProperty`）
   —— 返回 **err 87**。把属性 ID（49/50）、`ProtocolDataOffset`（0/36/44）、输入是否补齐到 48、
   缓冲长度（512/4096）四种维度穷举了 24 组合，全部 87。中间还踩了一个：属性 ID
   `StorageAdapterProtocolSpecificProperty` 是 49，`StorageDeviceProtocolSpecificProperty`
   是 **50**，只差一号；
3. `Get-StorageReliabilityCounter` —— 一次给真值：Samsung 860 EVO **26805 小时**、
   ST500LM021 **6416 小时**。

`core/diskinfo.py` 因此是**全项目唯一用 PowerShell 的模块**，理由写在文件头：这是唯一在
真机上验证过的路径。代价 1.9 秒，所以和激活信息一样走后台线程 + 5 分钟缓存。

**NVMe 的通电小时数 Windows 不上报**（本机 WDC SN520 的 PowerOnHours 是空值，`Get-
PhysicalDisk` 的其他字段都正常）。界面显示「—」，tooltip 明说「与权限无关」。

解析上两个坑：

- PowerShell 的**单引号字符串不处理转义**，`'{0}`t{1}' -f …` 会原样输出两个字符 `` `t ``。
  分隔符改用 `-join [char]9`。
- 先 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`，再用 `utf-8 → mbcs → gbk` 兜底解码。

**布局连带改了四处**（页面从 7 张卡变 8 张，不收拾就塞不下）：

- 「显卡」卡并进「显示与网络」—— 它只有一行内容，却占掉整格高度，右下角大片空白；
- 「主机名」删掉，它和「计算机名」是同一个值（都来自 `gethostname()`）；
- 系统卡加「整机型号 / 整机序列号」，主板卡加「主板序列号」；
- `InfoRow` 的 value 加 `QSizePolicy.Ignored`。QLabel 的 `minimumSizeHint` 按整段文本算，
  40 字符的 NVMe 序列号会把整列顶宽，980 宽的窗口下右边那一列直接被挤出可视区
  （改之前实测被裁掉约 30px）。设成 Ignored 后只吃剩余空间，放不下的裁掉、tooltip 兜底。

**顺带修掉一个换肤后页面变空的偶发 bug。** 系统信息页的首次加载原来挂主窗口的
`LAZY_STARTERS`，那是一条 `QTimer.singleShot(0, page, page.refresh)`。换肤重建页面后
实测约 **1/3 概率**这个定时器不落地，整页停在全横杠状态（连「版本」都是空的）。
改用 `showEvent` 首次显示时同步加载 —— 这是 `QStackedWidget.setCurrentWidget` 直接发出的
信号，不经过事件队列，不会丢。`LAZY_STARTERS` 里那一项已删，连跑 6 次未复现。

### 6.32 关闭窗口：从「关不掉」改成问一句

v0.0.35 之前 `Settings.minimize_to_tray` 默认 `True`，点关闭按钮的唯一结果是把窗口藏进托盘。
问题不在「要不要托盘」，而在**点叉没有任何可见反馈**：窗口消失、任务栏图标也没了，
用户第一反应是程序卡死或者被杀，于是反复点、反复点。

换成三态 `close_action`（`ask` / `tray` / `quit`），默认 `ask`：

- 点叉先弹一个 430px 的对话框：标题、一句说明、「记住我的选择」、三个按钮
  （取消 / 最小化到托盘 / 退出程序）。缩到托盘是安全侧，做成主按钮并吃回车；
  退出靠最右，挨着标题栏的叉；
- 勾「记住」才落成固定动作，写进 `config.json`；不勾就每次都问；
- 设置页「启动与窗口」把原来的开关换成下拉，档位同名；对话框里「记住」的结果会同步过去；
- 托盘右键的「退出」不走这套 —— 那里语义明确，直接退。

`minimize_to_tray` 字段已删。`Settings.load()` 是按默认值的类型逐键过白名单的，
不认识的键直接丢，所以老配置里的 `minimize_to_tray` 不会报错，也不会把默认值带偏，
升级后第一次关窗口就会问。

**顺带修掉一个真 bug：以前的「退出」其实退不干净。** `main.py` 里的
`setQuitOnLastWindowClosed(False)` 是给「关到托盘」那条路留的，所以 `closeEvent`
里 `event.accept()` 之后窗口没了、托盘也 `hide()` 了，事件循环却还在跑 ——
留下一个看不见、点不到的进程，只能去任务管理器结束。现在退出统一走 `_quit_now()`
（`_shutdown()` + `QApplication.quit()`），`closeEvent` 与托盘「退出」共用同一条路。

`tools/check_close.py` 覆盖五条：ask 取消（窗口留着、配置不动）、ask 选托盘并记住
（隐藏 + 落配置）、tray 直通、设置页下拉同步、quit（事件循环停、托盘摘掉）。

**样式表补了 `QDialog` 的背景。** 原来只给 `QMainWindow / #Root / #PageArea` 设 `BG`，
对话框不在这个体系里，深色主题下就是系统白底 —— 白底配深色按钮，截图一看就露馅。
`PowerModeDialog` 和所有 `QMessageBox` 跟着受益。标题栏也一起处理：`_apply_titlebar`
抽成模块级 `apply_titlebar_theme(widget)`，对话框在 `showEvent` 里调一次。

### 6.33 界面形态：切角面板、HUD 标题带、可折叠侧栏

v0.0.37 的一轮形态改造，与配色无关，先做形态后配色是刻意的 —— 形状定了，
颜色才有地方落。

**面板切角**（`components.panel_path / paint_panel`）。`Card` / `KpiCard` 从
「QFrame + QSS 圆角框」改成 `QPainterPath` 自绘：右上角切 14px 斜角、取消四边
等重描边、只留顶边 1.6px 高光线。

**一个必须记住的坑：不要给容器设带通配符的 `setStyleSheet`。** 一旦写了
`Card { ... }` 或 `QFrame { border: ... }`，样式会级联到卡片里所有子控件，
按钮边框被冲掉、输入框变成方块。切角必须自绘，不能靠样式表。

**标题带 HUD 化**。26px 大标题 + 副标题原来占 70px，压到 44px：左侧通道号
（`02 │ 性能监控`）+ 右侧 CPU/内存/磁盘 体征胶囊 + 底部一条基线。体征数据来自
`on_metrics` 每秒一帧，`Vitals.UNIT_W` 固定，宽度不够时**从右往左少画几个**
（980 窗口下自动只剩两个），不会把右边按钮挤出去。

**侧栏可折叠**。`NavButton.set_compact()` 只保留居中图标，文字进 tooltip；
宽度 228 ↔ 66（`SIDEBAR_WIDTH_COMPACT`），状态存 `Settings.sidebar_collapsed`。
收起后主内容区多出 160px，磁盘空间、软件专清这类分栏密集的页面少滚一屏。

**全局动作按钮降到 30px、标题降级**：一屏只该有一个实心强调色按钮，
页面自己的主按钮才是那一屏的焦点。

### 6.34 配色：深空仪表

底色冷调深蓝黑（`#0A0E13` / 面板 `#121A23`），强调色品牌青 `#2DD4BF`。
不是「Win11 语义色 + 系统强调色」那套办公软件观感。

**同一颗色种子喂两套主题**：深色往白提 26%，浅色往黑压 32%。浅色必须压得更狠 ——
`#2DD4BF` 在白底上对比度只有 1.8:1，当文字根本读不清。

配套的三个派生规则（都在 `theme_dark.py`）：

- `panel_edge()` 往 **ACCENT** 混（深 18% / 浅 30%），不是往正文色混。
  中性灰边只会让面板显得普通，带一点冷青才是仪表盘的感觉。浅色底本来色淡，
  不加重到 30% 根本看不见轮廓。
- `mem_colors()` 把内存构成从红/黄/绿换成 亮青 → 暗青 → 中性灰。
  内存占 60% 是正常状态，画成红灯会让整页一直像在报警。
- 侧栏选中态统一 `ACCENT_SOFT` 底 + `ACCENT` 文字。原来浅色用 `PANEL_SUNKEN`
  （灰），和侧栏底色几乎同色 —— 选中等于没选。

**语义色仍然独立**：红只用于真正的错误/告警，绿只用于「达标」。别为了统一
把红绿也染成青，那样告警就失效了。

### 6.35 卸载残留：先证明它有主，才敢说它是残留

`core/leftover.py` + 「软件管理 → 卸载残留」分段。这是全项目风险最高的功能，
判断依据是**猜**：软件卸载了，它留在 `%LOCALAPPDATA%` 的缓存通常还在，但目录名和
软件名之间没有任何强制约定（VS Code 用 `Code`、微信 4.0 用 `xwechat_files`）。

**四道闸门，任何一道不过就不列：**

1. 只扫 `%LOCALAPPDATA%` / `%APPDATA%` / `%PROGRAMDATA` 的**第一层子目录**，不递归
2. 硬白名单 `ALWAYS_KEEP`：系统组件、运行时、公共容器写死，不做规则推导
3. 认领判定，命中任一条就出局：已安装软件名/发行商（归一化双向包含）、
   安装路径前缀、**正在运行的进程名**、**磁盘根或 Program Files 下的同名文件夹**
4. 界面默认全不勾，删除进回收站

**第 3 条的后两项是踩出来的。** 第一版只有前两项，结果把这台机器上
`E:\ApkStart` 的数据目录（13 GB）列成了残留 —— 它装在盘根、不写注册表、
没有卸载器，`list_installed` 完全看不见。补上进程名和「盘上有没有同名程序目录」
之后，候选总量从 13250 MB 降到 201 MB。

**`remove()` 不信任界面传来的路径**：逐个重新校验父目录必须是那三个根之一。
实测传 `C:\Windows` 和桌面路径都被拒。

**`CheckBox` 默认是勾上的**（清理页要「全选」），残留页必须显式
`setChecked(False)` —— 忘了一行就等于替用户预先勾了删除项。

**风险按「最近有没有动过」分级**，这是唯一可靠的旁证：卸载半年没动过的目录，
和昨天还在写的目录，风险完全不同。7 天内改动过的标红。

### 6.36 长文本一律用 ElidedLabel

用户的原话是「有的字都不显示了」。根因不是排版，是 **QLabel 放不下时直接裁掉，
不画省略号** —— 右边半个字都不剩，看着像没加载完。而且它的 `minimumSizeHint`
按整段文本算，一个 36 位 NVMe 序列号就能把整列顶宽，小窗口下右列被挤出可视区。

`components.ElidedLabel` 自绘：超宽画「…」，完整内容进 tooltip，右键可复制
（自绘之后没有框选能力，复制得另开口子）。`sizeHint` 不参与布局，宽度由父布局给。

用于两处：`page_sysinfo.InfoRow` 的值（处理器型号、BIOS 版本号都受益），
以及存储设备卡的三个副信息行。

**存储卡从两行改三行**（型号 / 规格 / 序列号）：原来两行各塞四五项，窄窗口必截。
序列号用等宽 10px，36 位串在 980 最小窗口刚好放得下（252px vs 可用 258px）。
标签列宽度定为 40px —— 实测「磁盘 0」33px、「磁盘 10」39px，省下来的 20px
正好够序列号不画省略号。

顺带清掉两个数据噪音：`hours is None` 时不再输出「通电 —」（整段省掉，说明进
tooltip）；`diskinfo._parse` 里序列号 `rstrip(".")`，部分 NVMe 盘自己上报的
序列号末尾带句点，显示出来像打错字。

### 6.37 日志与「读取失败 ≠ 没有」

v0.0.39 补的两件事，动机都来自同一个问题：**出问题时手上没有任何线索。**

**日志（`core/applog.py`）。** 之前全项目 `grep logging` 是 0，同时有 50 处
「吞掉异常继续跑」。降级本身是对的，错的是连一行字都不留 —— 用户看到空列表或
「—」，分不清是没数据还是读失败。

- 写 `%APPDATA%\MemoryKeeper\logs\app.log`，1 MB × 5 份滚动
- 每进程开头写一段环境信息（版本 / Python / 是否管理员 / 系统版本）
- `install_excepthook()` 接 `sys.excepthook` + `threading.excepthook`，
  未捕获异常落盘后弹一次提示，带「打开日志目录」
- 打包成 `--windowed` 后 `sys.stderr/stdout` 是 None，PySide6 在槽函数里
  捕获的异常原本直接消失（不走 excepthook）→ `capture_stderr()` 把它接进日志
- 关于页新增「导出诊断信息」：环境摘要 + 日志尾部写成文件，路径自动复制

**`applog.silenced(where)` 是留痕的标准入口。** 别写裸 `except: pass`，
也别在降级处写 `logging.debug` —— 前者没记录，后者没人管格式。
`where` 用「模块.函数」，日志里能直接定位。

**同一个位置 5 分钟内只记一次。** 指标采集每秒一轮，某个传感器持续失败会在
一小时内写满 1 MB，把真正有用的信息挤掉。整块功能失败用 `applog.failed()`
（WARNING 级），逐项采集用默认的 DEBUG。

**读取失败要说出来，不能伪装成空。** 两个典型：

| 位置 | 原来 | 现在 |
|---|---|---|
| `startup._run_schtasks` | 失败返回 `""` → 0 条任务 →「没有第三方计划任务」 | 返回 `None`；`startup.last_errors()` 带出原因；页面显示琥珀色「读取失败 · 悬停看原因」 |
| `diskinfo._run` | PowerShell 失败返回 `""` → 空列表 →「未检测到物理磁盘」 | `diskinfo.last_error()` 带出原因；卡片显示「读取失败」+ 悬停看原因 |

`StartupState` 因此多了一个 `errors: dict` 字段，页面按分段只显示相关来源的错误。
实测（沙箱里 schtasks 被安全策略拦掉）三处来源里只有「计划任务」报错，
「全部」段显示 `6 项 · 已启用 6 · 有来源读取失败`，其余来源照常列出。

### 6.38 体检与清理的分工：硬件归硬件，垃圾归垃圾

v0.0.40 的信息架构调整，起因是一个误读：**「72 分」到底在说什么？**

11 个评分项里 8 个是垃圾/空间类（剩余空间 28、垃圾 12、重复 8、软件缓存 8、
注册表 4、更新积压、可释放系统文件），真正的硬件健康只有 3 项（磁盘 11、
文件系统与对齐 7、容量 5）。也就是说那个分数在衡量「你垃圾多不多」，
而用户会读成「我的硬盘要坏了」。

**做法一：因子分两类。** `Factor` 加 `kind` 字段（`hardware` / `cleanup`），
`HealthReport` 提供 `hardware_score` / `cleanup_score`，各自按组内权重
归一化到 100。没测到的项不计入分母 —— 否则会凭空拉低分数，用户找不到原因。

**做法二：体检页只算可清理项**，标题改成「可清理项评分」，副标题写明
「硬件状态见系统信息」。硬件三项独立成卡，挂在系统信息页（`HealthPage`
不再渲染它们，`self.rows` 用不满会自动隐藏）。

**做法三：社交缓存只留一个出处。** `cleaner` 里原来有微信/QQ/企业微信/钉钉
四条规则，`appclean` 整页做的是同一件事 —— 同一批目录两个页面都能清、
各报一个体积，口径还不一样（这边按目录类型，那边按软件聚合）。四条规则
已删，`core/social.py` 一并删除（早被 appclean 取代，只剩 docstring 引用）。

为此新增 `store.AppCleanState`：明细仍留在页面上（几百个目录、逐类勾选状态
塞进 store 要维护两份），store 只存 `total / apps / scanned_at`，
体检和顶部「可释放」从这里读。清理完调 `store.apply("appclean_scan", stats)`
重算，否则数字会挂着不动。

**还没做的一步**：清理组现在仍是 5 个入口（垃圾清理 / 软件专清 / 重复文件 /
磁盘空间 / 回收中心），计划收成「清理中心（分段）+ 空间分析」两个。
这需要在 `main_window` 加一层壳 + 把 62 处 key 引用改掉（`LAZY_STARTERS`、
`NO_OPTIMIZE_PAGES`、`FACTOR_PAGE`、`reclaimable_parts`、快捷键、跨页跳转），
改动面比前两步大一个量级，单独一轮做，别夹在别的改动里。

### 7.1 界面

| 坑 | 现象 | 解法 |
|---|---|---|
| 按钮点完把自己禁用了 | 永久停在「扫描中…」，只能重启 | 用 `QThread.finished` 做兜底恢复，**任何会禁用自身的按钮都必须有一定会执行的恢复路径** |
| `QToolTip { background-color: ... }` 写了却还是黑底 | 触发控件自己 setStyleSheet 过（本项目 label 全都写过 color），tooltip 就不再认全局 QSS 规则，底色回落到系统调色板；深色系统下是纯黑。挂到 Root/Card/控件自身、改 palette 都试过，不稳定 | 别修样式了，自绘一个（`ui/tooltip.py`），应用级过滤器接管 `QEvent.ToolTip`。详见 6.14 |
| 卡片里只有固定高度的行 | 多余高度被标题行吃掉，行被推得七零八落 | 标题 holder `setFixedHeight`，卡片底部 `addStretch(1)` |
| refresh 时只删按钮 | `addStretch` 累积，按钮越刷越靠右 | 布局 `takeAt(0)` 全部清空再重建 |
| `QMessageBox.exec()` 写在任务回调里 | 阻塞事件循环，后面的任务全卡住 | 改 `show()` + `WA_DeleteOnClose` |
| `QTimer.singleShot(0, self._method)` 跨换肤 | `RuntimeError: libshiboken: Internal C++ object already deleted` —— 换肤重建会销毁旧页面，延后一帧的回调再去碰按钮就炸 | 用带 context 的重载 `QTimer.singleShot(0, self, self._method)`，context 销毁后回调不再触发 |
| 带 context 的 `singleShot` 也会静默丢 | 系统信息页换肤后有约 1/3 概率停在「全横杠」，连「版本」都是空的，日志里没有任何异常——定时器没落地，回调根本没执行 | 纯展示页的首次加载改挂 `showEvent`（`QStackedWidget.setCurrentWidget` 同步发出，不经过事件队列）。只有确实要「等布局稳定」的场景才用 singleShot |
| 长字符串把整列顶宽 | 40 字符的 NVMe 序列号让 980 宽的窗口右边那列被挤出可视区（实测裁掉约 30px） | `QLabel` 的 `minimumSizeHint` 按整段文本算。给 value 设 `QSizePolicy.Ignored` 让它只吃剩余空间，裁掉的靠 tooltip 兜 |

### 7.2 Windows API

| 坑 | 说明 |
|---|---|
| SMBIOS 返回的不是裸表 | 前面有 8 字节 `RawSMBIOSData` 头（Used20/Major/Minor/DmiRevision/DWORD Length），从偏移 0 解析会把首字节当 type |
| SMBIOS 字符串区收尾长度不固定 | 有 N≥1 个字符串时收尾 **1 个** `\0`；零字符串时是 **2 个**。判据看后一字节是否也是 0 |
| SMBIOS 的 CPU Max Speed 不可信 | 某主板把 i3-9100T 写成 8300 MHz。优先用注册表 `~MHz` |
| 提权实例占着互斥量 | `CreateMutexW` 返回 **NULL + ERROR_ACCESS_DENIED(5)**，不是 183。只判 183 会让第二个实例照常启动 → 两个同名窗口 |
| 硬盘 SMART 直通被拦 | `IOCTL_SMART_RCV_DRIVE_DATA` 返回 err 5；NVMe 日志页 `StorageDeviceProtocolSpecificProperty` 返回 err 87（属性 ID、偏移、补齐、缓冲长度穷举 24 组合皆不通）。注意 `StorageAdapter…` 是 49、`StorageDevice…` 是 **50**，差一号 | `Get-StorageReliabilityCounter` 是唯一验证过的路子（见 6.31） |
| PowerShell 单引号不转义 | `'{0}`t{1}' -f …` 原样输出 `` `t ``，解析出来每一行只有一列 | 分隔符用 `-join [char]9`，或改用双引号字符串 |
| 回收站没有 COM 依赖 | 项目没装 pywin32，改解析 `$Recycle.Bin` 的 `$I` 元数据（v2：8B 头 / 8B 大小 / 8B FILETIME / 4B 路径长度 / UTF-16LE 路径） |
| CLSID 全枚举很慢 | 上万个键，先枚举成 list 再筛会慢十倍。要**边枚举边判断、够数就停** |
| Restart Manager 查占用 | `RmGetList` 要先拿空缓冲区调一次（返回 234 `ERROR_MORE_DATA`）才知道需要几条；`pnProcInfo` 传的是**条数容量**不是字节数。缓冲区要按 `needed` 条开 `RM_PROCESS_INFO` 数组，小了会只返回一半 |
| 关浏览器缓存要整棵树 | RM 报的常常是渲染进程，只关它主进程立刻把缓存写回来。要顺着**同名 exe 的父链**找到主进程，整棵进程树一起关 |

### 7.3 工程习惯

| 坑 | 说明 |
|---|---|
| **批量替换静默失败** | 用 heredoc + `str.replace` 改代码，匹配不上时**不报错**。本项目栽了 6 次（`_on_watchdog`、`_on_health_data`、`activate_existing`、`registry_count`、`has_registry`、`\n` 被写成字面 `/n`）。**改完必须 grep 确认，不能只看 compileall 通过** |
| 短匹配串会误伤 | `from core import bigfile` 会命中 `from core import bigfile, trash`。**改导入语句要把整行作为匹配串** |
| `QTest.mouseMove` 在离屏环境无效 | 不触发 `mouseMoveEvent`，验证绘制逻辑要**直接改状态变量再 `update()`** |
| **按索引切片替换方法体** | 用 `t.index(a)` ~ `t.index(b)` 切片时，若 b 在 a 之前，`t[:a]+new+t[b:]` 会**复制中间整段代码**。替换方法体前先断言 `end > start` |
| **`switch_page` 静默返回** | 找不到 key 时直接 `return`，导航项和 `_pages` 对不上时界面点着没反应、测试也不报错。现已加 `[nav] 页面不存在` 警告，回归测试必须断言 `_current_page == key` |
| **换肤后懒加载标志没重置** | `_rebuild_for_theme` 会重建所有页面，但只重置了 3 个标志，系统信息页换肤后全是横杠。现在用 `LAZY_FLAGS` 统一登记、统一清零。**新增懒加载页面时必须加进这个清单** |
| **重建后 central widget 不显示** | `_build_ui()` 里 `setCentralWidget(root)` 之后**必须 `root.show()`**。否则换肤 / 跟随系统主题（4 秒一次的 `_theme_watch`）重建时，新 widget 停在隐藏态，整个窗口只剩一片底色 —— 界面看着像崩了，其实只是没显示。真机上改系统深浅色就会踩到 |
| **概览动作只跳转不执行** | 「做一次全面体检」原来只 `switch_page("health")`。现在走 `_navigate_action`，特殊 key `__full_check__` 会跳页并派发任务 |
| **凭旧印象改结构** | 曾把用户已重构成「MonitorPage 壳 + 12 项导航」的结构，用旧版 17 项覆盖回去，导致 5 个页面点不动。**改导航/架构前先读现状，别信记忆** |

## 八、构建、版本与回滚

### 8.0 版本号与回滚（2026-11-08 新增）

**版本号唯一来源是 `core/version.py`**（当前 `0.0.1` / `内测`）。
窗口标题、托盘提示、设置页底部、归档产物名都从这里读。

```bash
python tools/build.py            # 用当前版本打包 + 自动归档到 releases/vX.Y.Z/
python tools/build.py --bump     # 先把 PATCH +1 再打包（发新版用这个）
python tools/build.py --no-archive

python tools/releases.py              # 列出所有归档版本
python tools/releases.py --to 0.0.1   # 回滚到该版本
```

归档内容：`releases/vX.Y.Z/` 下有 `source.zip`（65 个源文件）、
`Windows系统管家-vX.Y.Z.exe`、`manifest.json`（版本/时间/文件数）。

回滚会先**把当前状态备份**到 `releases/_rollback_时间戳/`（保留最近 3 份），
再解压源码、替换 exe。所以回滚本身也能反悔。
恢复只覆盖 zip 里已有的文件，不删除新增文件。

**刻意没用 git**：项目一直没有版本控制，一个能列版本、能一键回滚的脚本更实用。

```bash
python tools/build.py
```

流程：探测 `dist/` 是否被占用 → PyInstaller onefile → 输出约 37 MB 单文件 exe。

### 8.1 启动即申请管理员（UAC）

`tools/build.py` 里带 `--uac-admin`，生成的 exe manifest 是
`requestedExecutionLevel level="requireAdministrator"`，双击时由 Windows 弹 UAC。
清理 system32/Temp、写 HKLM 注册表、结束高权限进程都需要它，否则用户点下去
全是「拒绝访问」。

两个坑：

- **`build.py` 会重写 `build/*.spec`**。只改 spec 里的 `uac_admin=True` 没用，
  下次 `python tools/build.py` 就把 spec 盖回去了。配置必须写在 build.py 的命令行里。
- **开机自启会每次弹 UAC**。自启走的是注册表 Run 键，普通权限写不进去、
  高权限又需要授权。要么别开自启，要么改用任务计划程序（最高权限运行、免提示）。
  目前没做任务计划方案。

源码 `python main.py` 不提权（manifest 只对 exe 生效），界面左下角会显示
「普通权限 · 点击提权」，点了走 `ShellExecuteW runas` 重启，这是开发时的正常状态。

**注意**：Windows 会缓存任务栏图标。换了图标后如果任务栏没变，
需要「取消固定再重新固定」或重启资源管理器。

### 8.4 推送到 GitHub

仓库：https://github.com/jtnetcc/windows-manager （**已公开**）

**本机 `git push` 不可用** —— 网络只放行 `api.github.com`，`github.com` 被代理拦掉
（`CONNECT tunnel failed, response 502`）。`git fetch` 偶尔能通，`push` 一律不通，
所以别在这上面浪费时间去试凭据。

正式路径是仓库自带的工具：

```bash
set GH_TOKEN=ghp_xxx
python tools/push_github.py --repo jtnetcc/windows-manager -m "feat: xxx"
python tools/push_github.py --repo jtnetcc/windows-manager --dry-run   # 只列文件
```

`tools/push_github.py` 做的是：blob → tree → commit → 移动 main。token 只从环境
变量读，不写任何文件。

四个坑：

- **空仓库不能建 blob**（409 Git Repository is empty），要先有至少一次提交
- **中文路径会被转义**（`\350\260\203`），必须 `git -c core.quotepath=false`
- **内容要从 git 对象取，不能读磁盘**（2026-11-14 修）。开了 `core.autocrlf` 时
  工作区是 CRLF、仓库里是 LF，直接 `open()` 会把每个文件都变成整文件重写：
  远端 tree 哈希和本地 HEAD 对不上，GitHub 上的 diff 糊成一片。现在走
  `git cat-file blob :path`，实测推送后 tree 哈希与本地完全一致
- **多提交会被压成一个提交**。API 建的是单个 commit，本地 N 个提交到了远端只有
  一条。提交信息里写清楚，免得日后对不上

**当前状态（2026-11-14）**：本地 `main` 是 30 个提交的正史，远端 `main` 是它压成
一条的版本（`87102f19`，tree 哈希与本地完全相同，内容零差异），标签 `v0.0.38`
打在同一个提交上。等 `github.com` 恢复后可以把正史还回去：

```bash
git fetch origin
git push --force origin main
git push --force origin :refs/tags/v0.0.38 && git push origin v0.0.38
```

内容一致，force 只改历史形状，不会丢任何文件。

### 8.5 同步到阿里云 OSS

```bash
set OSS_AK=LTAIxxx
set OSS_SK=xxx
python tools/sync_oss.py              # 上传当前版本 + latest
python tools/sync_oss.py --private    # 只传不公开
```

上传两个对象（都设 public-read，桶本身权限不动）：

```
windows-manager/vX.Y.Z/Windows-Manager-vX.Y.Z.exe
windows-manager/latest/Windows-Manager.exe
```

- 桶名与 Endpoint 从环境变量 `OSS_BUCKET` / `OSS_ENDPOINT` 读，**源码里不写死**
  （仓库是公开的，写死等于把分发地址公开）
- 没装 oss2 SDK，签名用标准库手写：StringToSign → HMAC-SHA1 → base64
- **`x-oss-object-acl` 要参与签名**（按字典序拼进 CanonicalizedOSSHeaders），漏了会 403
- 凭证只从环境变量读，不写文件

### 8.6 一键发版

```bash
set GH_TOKEN=ghp_xxx
set OSS_AK=LTAIxxx
set OSS_SK=xxx
python tools/release.py
```

做四件事：`build.py --bump`（递增+打包+归档）→ 本地提交 →
`push_github.py`（推源码）→ `sync_oss.py`（传 exe）。

常用参数：

| 参数 | 作用 |
|---|---|
| `--no-bump` | 重发当前版本 |
| `--skip-github` | 只打包 + 传 OSS |
| `--skip-oss` | 只打包 + 推 GitHub |
| `--dry-run` | 只看会做什么 |
| `-m "..."` | 提交信息 |

**有一个保护**：打包时如果旧版还在运行，exe 会落到 `dist_pending/`，
`dist/` 里还是旧的。脚本检测到 `dist_pending/` 非空会**直接中止**，
避免把旧包当新包发出去。

### 8.7 仓库是公开的：禁止提交敏感信息
